- **NEW: Phase 3c wedge research — recommend Path B (`deploy_role_v2` thin wrapper).** Cycle 1541. Full wedge picture below; recommendation is Path B.

  **Where the `## Aliases` registry is populated:** Not by `wizard.build_config_md` — it doesn't emit the section at all (audit `references/scripts/wizard.py` lines 660-768). Existing installs carry a legacy **bullet form** (`- **skill**: skill`) written by an older installer; this repo's own `.squidsquad/config.md` lines 14-19 is the canonical example. The v2 parser `config.parse_aliases_registry` accepts both the canonical 3-column table AND the bullet-form fallback (`config.py` lines 458-466, `_parse_aliases_bullet_form` legacy shim). So fresh v2 installs created by the current wizard would have NO `## Aliases` section and immediately fail at `deploy_alias_v2`'s registry lookup.

  **Contract gap audit (wizard → deploy_role vs deploy_alias_v2):**
  1. **Variant/compose_name vs alias.** Wizard's `compose_name` (`"worker-ios"` when variant set, otherwise `agent_id`) selects the v1 entry file. v2's equivalent is alias → `(role_class, l3_domain)` from the registry, walked by `v2_link_stage.collect_sources_for_validation`. Different mental model.
  2. **output_name ≠ alias.** Wizard passes `output_name=agent_id` distinct from `compose_name`. `deploy_alias_v2` writes to `<target_root>/.squidsquad/<alias>/` — alias IS the output directory.
  3. **SOUL.md seeding.** `deploy_role` calls `_assemble_and_write_soul(role_name, target_root, output_name)` when SOUL.md missing (compose.py:1548-1550). `deploy_alias_v2` does NOT seed SOUL.md.
  4. **Registry not populated by wizard.** Fresh installs lack the `## Aliases` section entirely; `deploy_alias_v2` aborts on missing-section.

  **Three paths:**
  - **Path A — extend `deploy_alias_v2`** to accept `output_name` + write SOUL.md. Bloats the canonical v2 entry point with wizard-specific concerns. Rejected: SOUL seeding is install-time, not compose-time; mixing the concerns muddies the v2 model.
  - **Path B — thin `deploy_role_v2(role_name, target_root, output_name)` wrapper** that resolves `role_name` → `(role_class, l3_domain)` via the existing variant convention, calls into the v2 link+assemble internals directly (NOT through the alias registry), writes three files to `<target_root>/.squidsquad/<output_name>/`, then calls `_assemble_and_write_soul`. Wizard's one call-site changes name only. **Recommended.**
  - **Path C — registry-first wizard.** Extend `build_config_md` to emit `## Aliases`, make `parse_aliases_registry` / `_read_config` accept a target_root, make `deploy_alias_v2` propagate target_root through the registry read, then wizard calls `deploy_alias_v2(alias, target_root=target_root)`. The most architecturally pure (alias registry is v2's source of truth) but largest blast radius — touches 3-4 modules and config.md schema. Should be its own PRD (`alias-registry-is-truth`), not an E6 sub-phase.

  **Why Path B:** smallest blast radius that lets E6 delete `deploy_role`. Keeps wizard's contract stable. SOUL seeding lives in the wrapper, mirroring v1. Two v2 entry points (`deploy_alias_v2` for compose-CLI alias deploys; `deploy_role_v2` for wizard's role-class direct deploys) is a documented split, not muddled API surface. The wrapper can later be removed if Path C is undertaken in a follow-up PRD.

  **Open question for PM/human:** confirm Path B before Phase 3d work commits the deletion of `deploy_role`. Either greenlight at next pickup, or post the Path A/B/C summary as a Discussion comment on #10685 first.
