# FEAT-4 Research — Boot Remote Agents Sub-Skill

**Feature**: #4 — PM auto-boots entire team on startup (scoped as a reusable sub-skill)
**Date**: 2026-04-11
**Status**: Research (Phase 1)
**Related**: Blocked by #335 (health_check.py) · Blocks installer auto-boot (Q-new21 follow-up to #328) · Adjacent to #250 (in-terminal auto-restart, shipped)

---

## Summary

Today, when a SquidSquad agent clone is missing a running Claude session (never started, crashed, stopped, or dead-terminal'd), nothing starts it back up. PM detects `👻 stalled` in its Step 7 health check, comments on tracker items, and leaves the human to manually run `./start-<role>.sh`. #250 solved in-terminal auto-restart (the wrapper loop that re-spawns `claude` inside an already-running terminal), but not the "no terminal at all" case.

This feature creates a **boot-remote-agents sub-skill** that PM (and later the installer) composes in. When invoked, the sub-skill spawns a **new terminal window** on the host OS that runs the target agent's boot script (`.squidsquad/start-<role>.sh/.ps1`) in its cross-clone path. The existing `start-role` wrapper (with PID lock, restart loop, stop-sentinel) handles everything from there — the sub-skill's only job is "make a terminal appear with the right script running."

It lives at `references/sub-skills/common/boot-remote-agents.md`, composes into `references/sub-skills/roles/pm-agent.md` as Step 7b (immediately after the health check so stalled agents get auto-revived in the same cycle), and is additionally composable by the installer's setup flow to boot the full team at the end of `/squidsquad-setup`.

Implementation is **feasible** but has three real constraints: (1) OS detection and per-OS spawn commands are non-trivial but well-understood, (2) false-positive re-boots are dangerous and require #335's `health_check.py` to ship first, and (3) the distinction between "stopped on purpose" (`.stop` sentinel) and "dead silently" (stale state, no PID) must be airtight.

## 2. Implementation Approaches

### Approach A: Pure-prose sub-skill, Claude executes bash/PS directly (LIGHTER)

The sub-skill is 100% prose instructions telling Claude: "If the OS is Windows, run `Start-Process wt.exe -ArgumentList 'pwsh', '-NoExit', '-File', 'path/start-<role>.ps1'`. If the OS is macOS, run `osascript -e 'tell app "Terminal" to do script "bash path/start-<role>.sh"'`. …"

**Pros**:
- Zero new Python code
- Transparent — every spawn command is visible in the cycle log
- Easy for the dev agent to edit prose templates

**Cons**:
- Prose is skippable (same failure mode as #335: PM takes shortcuts) — the PM agent could misremember which command to run and invent a broken one
- Logic for "detect OS → pick terminal emulator → fall back if unavailable → verify spawn succeeded" is non-trivial decision tree, fragile in prose
- Error handling in pure prose is unreliable
- Hard to unit-test

### Approach B: Python helper `boot_remote.py`, sub-skill calls it (RECOMMENDED)

The sub-skill is thin prose: "Run `python references/scripts/boot_remote.py <role>` and read its output. If exit 0, the agent was spawned (or skipped for a valid reason). If exit 1, log the error in qa-log.md and the discussion comment."

The helper handles:
- OS detection via `platform.system()` + `os.environ.get('WSL_DISTRO_NAME')`
- Terminal emulator detection (shutil.which for each candidate)
- Pre-flight: `.local-config` parsing, target clone path exists, boot script exists, `.stop`/`.pid` state
- Spawn using `subprocess.Popen` with platform-appropriate args
- Post-spawn verification: poll `<clone>/.squidsquad/<role>/current-state` for fresh mtime within N seconds
- Structured output (JSON with `--json` flag, pretty text otherwise)

**Pros**:
- Mirrors the pattern in #335 (`health_check.py`): prose → Python. PM cannot take shortcuts on mechanical work.
- Unit-testable (mock `subprocess`, fake `.local-config`, assert the right command is built)
- Single source of truth for OS detection, reused by installer later
- Clean JSON output consumed by PM cycle and (later) installer

**Cons**:
- ~150 lines of Python to maintain
- Subprocess + terminal spawning is tricky on Windows (detached process, console inheritance)

**Verdict**: **Approach B** is strongly recommended, matching the same architectural lesson from #335 ("prose is skippable, scripts are not"). Phase 2 should confirm.

### Approach C: Shell-only — new bash/PS helper scripts, no Python

Two new scripts (`references/scripts/boot_remote.sh` + `.ps1`) with the same logic in shell. Sub-skill picks which to call based on OS.

**Pros**: Avoids a new Python dep.
**Cons**: Already-duplicated logic; harder to unit-test; the repo already standardizes on Python for orchestration scripts (`cycle.py`, `tracker.py`, `git_ops.py`, `health_check.py`). New shell helpers break that convention.
**Verdict**: Rejected.

## 3. OS-Aware Terminal Spawning — Deep Dive

### Windows

**Candidates (in preference order)**:

1. **Windows Terminal (`wt.exe`)** — modern, preferred when available:
   ```powershell
   Start-Process wt.exe -ArgumentList "--window","0","new-tab","--title","squidsquad-skill","pwsh","-NoExit","-File","D:\path\.squidsquad\start-skill.ps1"
   ```
   or equivalent for Git Bash:
   ```powershell
   Start-Process wt.exe -ArgumentList "bash","-c","cd /d/path && bash .squidsquad/start-skill.sh; exec bash"
   ```

2. **Legacy `cmd.exe`** — universal fallback:
   ```cmd
   start "squidsquad-skill" cmd /k "cd /d D:\path && powershell -NoExit -File .squidsquad\start-skill.ps1"
   ```

3. **PowerShell `Start-Process`** — from an existing PS session:
   ```powershell
   Start-Process powershell -ArgumentList "-NoExit","-File","D:\path\.squidsquad\start-skill.ps1"
   ```

**Detection**: `shutil.which("wt.exe")` → use Windows Terminal. Fallback to `start cmd /k` via `cmd.exe /c`. From Python, use `subprocess.Popen([...], creationflags=subprocess.CREATE_NEW_CONSOLE | subprocess.DETACHED_PROCESS)` so the new console isn't a child of PM's process.

**Argument passing**: Arguments to the boot script (`--name <alias>`) are appended to the Popen args list. The boot script reads them with its existing `while [[ $# -gt 0 ]]` parser.

**Environment inheritance**: `CREATE_NEW_CONSOLE` + no `env=` kwarg → new process inherits PM's env, including `CLAUDE_API_KEY`, `PATH`, etc. Good default.

**Git Bash vs PowerShell for `.sh` vs `.ps1`**: Since `start-role.sh` and `start-role.ps1` are both generated from templates (see `compose.py boot-all`), the sub-skill picks `.ps1` on Windows by default. If Git Bash is preferred (detect via `shutil.which("bash.exe")` under `C:\Program Files\Git\usr\bin\bash.exe`), the `.sh` variant can be used — but v1 should default to `.ps1` for simplicity.

### macOS

**Candidates**:

1. **Terminal.app (default)** — always present:
   ```bash
   osascript -e 'tell app "Terminal" to do script "cd /path && bash .squidsquad/start-skill.sh"'
   ```

2. **iTerm2** — preferred by power users:
   ```bash
   osascript -e '
     tell application "iTerm"
       create window with default profile
       tell current session of current window
         write text "cd /path && bash .squidsquad/start-skill.sh"
       end tell
     end tell
   '
   ```

3. **`open -a Terminal.app <script>`** — simpler but less control:
   ```bash
   open -a Terminal.app /path/.squidsquad/start-skill.sh
   ```

**Detection**: Check `$TERM_PROGRAM` — if `iTerm.app`, prefer iTerm; otherwise Terminal.app. Alternatively, `ls /Applications | grep -i iTerm` / `osascript -e 'id of app "iTerm"'`. v1 can start with Terminal.app only and add iTerm as a refinement.

**Full-screen spaces / multi-desktop**: A spawned Terminal window appears on the current Space. If the user has Terminal pinned to a different Space, the window may pop up elsewhere. Not worth solving in v1 — document it.

**Gotcha**: `osascript` requires Terminal to have Accessibility permission to be scripted. On first use, macOS prompts the user. Not solvable by sub-skill; document as a known first-run hitch.

### Linux

**Candidates** (check with `shutil.which`):

1. `gnome-terminal -- bash -c "bash .squidsquad/start-skill.sh; exec bash"` (GNOME, default on Ubuntu)
2. `konsole -e bash -c "bash .squidsquad/start-skill.sh; exec bash"` (KDE)
3. `xterm -hold -e "bash .squidsquad/start-skill.sh"` (classic X11 fallback)
4. `xfce4-terminal --command "bash .squidsquad/start-skill.sh"`
5. `alacritty -e bash -c "bash .squidsquad/start-skill.sh; exec bash"`
6. `kitty bash -c "bash .squidsquad/start-skill.sh; exec bash"`
7. **`tmux new-session -d -s squidsquad-skill "bash .squidsquad/start-skill.sh"`** — fallback for headless / SSH / no-X11 environments

**Detection order**: Check `$TERM_PROGRAM`, `$XDG_SESSION_TYPE`, and `DISPLAY`. If no display (headless), fall back to tmux (if available). If no tmux either, refuse and print manual instructions.

**WSL**: `WSL_DISTRO_NAME` or `WSLENV` env var present → treat as "Linux inside Windows." Spawning a new terminal here is tricky — the user's terminal is likely Windows Terminal, but WSL bash doesn't directly launch Windows GUI apps by default. Options:
- Launch `wt.exe` (Windows Terminal) from WSL with `wt.exe -w 0 new-tab -- wsl.exe bash -c "cd ... && bash start-skill.sh"` (works if wt.exe is on PATH, which it is by default in WSL 2)
- Or fall back to tmux

**Headless/Docker/CI**: If no terminal emulator AND no tmux AND no DISPLAY, refuse. Sub-skill exits with "no spawn mechanism available" and prints the manual command the human should run.

### Fallback

All OSes: if the detected spawn mechanism fails (returncode != 0, or post-spawn verification times out), the sub-skill:
1. Logs the exact command attempted and its stderr to `pm/qa-log.md`
2. Appends a Discussion note on the agent's most recent tracker issue: `> [ts] **pm**: Attempted to auto-boot agent but terminal spawn failed. Please run manually: <command>`
3. Returns non-zero (but does not crash PM's cycle — PM continues to the next step)

## 4. Detection Logic — Who Needs Booting?

The sub-skill runs after PM's Step 7 health check. Step 7 already produces (or will produce, once #335 ships) an annotated list of agents with states: `healthy / stalled / unknown`. The sub-skill consumes that list and for each agent applies:

| `.stop` exists? | `.pid` alive? | `current-state` fresh? | Decision |
|-----------------|---------------|------------------------|----------|
| yes             | —             | —                      | **SKIP** — human explicitly stopped |
| no              | yes           | yes                    | **SKIP** — healthy, no action |
| no              | yes           | stale                  | **SKIP and warn** — terminal exists but agent is hung; spawning a second one risks PID-lock collision, not a rescue. Log a warning, let the human investigate. |
| no              | no PID file, or PID dead | stale               | **BOOT** — agent never started or crashed silently |
| no              | no PID file   | missing                | **BOOT** — fresh state, first boot |
| no              | no PID file   | fresh                  | **SKIP** — someone else just started it (race window) |

**Why not just "boot whenever stalled"?** The PID-alive + stale case is critical: an agent can be stuck in a long-running operation with the terminal still open. Spawning a second terminal triggers the PID-lock in `start-role.sh` which aborts cleanly ("already running"), so it's not catastrophic — but it's noisy and confuses humans. Better to skip and let PM log a "hung?" warning.

**Race condition** (two PMs try to boot the same agent simultaneously): the PID lock in the boot script is the final defense — the second `start-role.sh` sees the PID file, checks `kill -0`, and aborts. No corruption possible. The sub-skill should log "PID lock denied spawn — another boot in flight" as info, not an error.

**Dependency on #335**: The "fresh vs stale" determination requires reliable cross-clone path resolution and mtime reading. Today's prose-based health check is unreliable (see #335 bug description — PM hand-assembles commands incorrectly). This sub-skill **MUST NOT** ship until `health_check.py` is available; otherwise auto-boot will false-positive on healthy agents that PM misidentified as stalled.

Concretely: the sub-skill's Python helper should either (a) call `health_check.py --json` to get the authoritative per-agent state, or (b) share the same `.local-config` parser module — likely (a) is cleaner.

## 5. Sub-Skill Structure — Proposed Draft

Below is a concrete ~130-line starting shape for `references/sub-skills/common/boot-remote-agents.md`. The dev agent will refine; this establishes the shape.

```markdown
### Step 7b — Auto-Boot Stalled or Missing Agents

**Prerequisites**: Step 7 (Agent Health Check) must have just run and produced a per-agent
health map. This step consumes that map and spawns terminals for agents that need booting.

Print: `[🦑 HH:MM:SS] Checking for agents that need booting...`

**Config gate**: Read `Auto Boot Agents` from `config.md`. If `no` (default), skip this step
entirely — the human will boot agents manually. If `yes`, proceed.

```bash
python references/scripts/config.py get auto-boot-agents
```

**Invocation**: For each agent listed in `config.md` active agents (plus DM if installed),
invoke the boot helper:

```bash
python references/scripts/boot_remote.py <role> --json
```

The helper consults `.local-config`, cross-clone state, and spawning rules. It returns JSON:

```json
{
  "role": "skill",
  "decision": "boot" | "skip" | "refuse",
  "reason": "stopped-sentinel" | "healthy" | "pid-hung" | "no-clone" | "no-spawner" | ...,
  "spawn_command": "wt.exe -w 0 new-tab ...",
  "spawned": true | false,
  "verified": true | false,
  "elapsed_seconds": 3.2
}
```

**Decision rules** (enforced by boot_remote.py, not by this prose):
- `.stop` sentinel present → decision=skip, reason=stopped-sentinel
- PID alive + state fresh → decision=skip, reason=healthy
- PID alive + state stale → decision=skip, reason=pid-hung, log warning
- No PID or dead PID + stale/missing state → decision=boot
- No PID + fresh state (< 30s old) → decision=skip, reason=race-boot-in-progress
- No clone path in `.local-config` → decision=refuse, reason=no-clone
- Clone path unreachable / boot script missing → decision=refuse, reason=script-missing
- No OS spawn mechanism available → decision=refuse, reason=no-spawner

**Pre-flight checks** (all performed by the helper):
1. `.local-config` exists and contains the target role
2. Clone path exists on disk
3. `<clone>/.squidsquad/start-<role>.{sh|ps1}` exists
4. OS can be detected
5. At least one terminal emulator is available

**Spawn command templates** (selected by the helper based on OS):

- **Windows + Windows Terminal**:
  `wt.exe -w 0 new-tab --title squidsquad-<role> pwsh -NoExit -File <clone>\.squidsquad\start-<role>.ps1`
- **Windows + fallback cmd**:
  `cmd.exe /c start "squidsquad-<role>" powershell -NoExit -File <clone>\.squidsquad\start-<role>.ps1`
- **macOS + Terminal.app**:
  `osascript -e 'tell app "Terminal" to do script "cd <clone> && bash .squidsquad/start-<role>.sh"'`
- **macOS + iTerm2**:
  `osascript -e 'tell application "iTerm" to create window with default profile command "bash <clone>/.squidsquad/start-<role>.sh"'`
- **Linux + gnome-terminal**:
  `gnome-terminal --title=squidsquad-<role> -- bash -c "cd <clone> && bash .squidsquad/start-<role>.sh; exec bash"`
- **Linux headless + tmux**:
  `tmux new-session -d -s squidsquad-<role> "cd <clone> && bash .squidsquad/start-<role>.sh"`

**Post-spawn verification**: After spawning, the helper polls
`<clone>/.squidsquad/<role>/current-state` for up to 30 seconds, checking for a fresh
mtime (newer than the pre-spawn mtime). If it updates, spawn is verified. If it doesn't
update within 30s, spawn is reported as unverified (but not necessarily failed — the
agent may be slow to initialize).

**Failure handling**: For each agent where the helper returns `decision=refuse` or
`spawned=false`, PM:
1. Writes a warning line to `pm/qa-log.md` with the role, reason, and attempted command
2. Appends a Discussion note on the agent's most recent open tracker item:
   > [YYYY-MM-DD HH:MM] **pm**: Auto-boot attempt failed (`<reason>`). Please run manually: `<command>`
3. Continues to the next agent — never crashes the cycle on a spawn failure

**Rate limiting**: The helper maintains `.squidsquad/pm/boot-attempts.log` (role, timestamp
pairs). If the same role has been boot-attempted within the last 10 minutes, the helper
returns `decision=skip, reason=recently-attempted`. This prevents spawn-spam when an agent
is crashing fast and PM detects it every cycle.

**Success logging**: For each successful boot, append to `pm/qa-log.md`:
```
## Auto-Boot — YYYY-MM-DD HH:MM
- **Agent**: skill
- **Spawned**: yes (verified in 4.2s)
- **Command**: wt.exe -w 0 new-tab --title squidsquad-skill pwsh -NoExit -File ...
```

And append a Discussion comment to the agent's most recent open tracker item:
```
> [YYYY-MM-DD HH:MM] **pm**: Agent was stalled — auto-booted successfully. Verified active in 4.2s.
```
```

## 7. Integration with #250 (Auto-Restart, shipped)

#250 and #4 are **orthogonal but complementary**:

| Dimension | #250 (auto-restart wrapper) | #4 (boot-remote-agents sub-skill) |
|-----------|------------------------------|------------------------------------|
| Context | Inside an already-running terminal | Across terminal boundaries |
| Trigger | `claude` process exits (context pressure, crash, cron expiry) | External agent (PM) detects missing/stalled via file system |
| Mechanism | `while true; do claude ...; done` in boot script | `Start-Process` / `osascript` / `gnome-terminal` |
| Actor | The boot script itself (bash/PS wrapper) | PM's cycle (or installer's final step) |
| PID lock | Acquires and holds the PID file for the role | Respects the PID file — if held, skips |
| Stop sentinel | Wrapper checks `.stop` between restart iterations | Sub-skill checks `.stop` before attempting to spawn |
| Output | `restart-log.txt` — per-role restart history | `pm/qa-log.md` + per-issue discussion comments |

**Shared code**: None directly, but both rely on the same artifacts:
- `.squidsquad/<role>/.pid`
- `.squidsquad/<role>/.stop`
- `.squidsquad/<role>/current-state`
- `.squidsquad/start-<role>.{sh|ps1}` (the wrapper)

**Interaction scenarios**:
1. PM spawns a fresh terminal → wrapper starts → wrapper runs `claude` → agent runs cycle. Works.
2. PM spawns a terminal while `.stop` exists → `start-role.sh` would proceed past `.stop` check (it removes `.stop` on first iteration) — but the sub-skill's §4 decision logic already skipped this case, so we never get here.
3. Agent context-pressure-exits → wrapper restarts it → status-bar shows `restarting` → PM's next cycle sees fresh state → no-op. Works.
4. Wrapper hits MAX_RESTARTS=50 and gives up → writes `error|Max restarts reached` → state file goes stale → PM sub-skill sees no PID → attempts to boot → PID lock is gone, boot succeeds. Works — this is the main value-add for #4 over #250 (#250 alone can't recover a max-restart shutdown).
5. Terminal window is manually closed by human → wrapper and `claude` both die → PID file not cleaned up if `kill -9`-style close → next cycle: PM sees stale PID (`kill -0` says dead), stale state → boots fresh terminal. Works.

## 8. Side Effects

| # | Side Effect | Severity | Mitigation |
|---|-------------|----------|------------|
| 1 | False-positive re-boot (PM misidentifies healthy agent as stalled, spawns duplicate terminal) | **H** | Block on #335 (`health_check.py`). The sub-skill's first pre-flight must be "authoritative state from health_check.py, not from prose." Config gate defaults to `no`. |
| 2 | Spawning a terminal without user permission / startling the user | **M** | Opt-in via `Auto Boot Agents: yes` in config.md. Setup flow asks the user during install. Document prominently. |
| 3 | Race: two PMs in two clones attempt to re-boot the same agent simultaneously | L | PID lock in `start-role.sh` is final defense — second spawn aborts cleanly. Sub-skill's rate limiter (`boot-attempts.log`, 10-min cooldown) further reduces noise. |
| 4 | Environment variable divergence — spawned terminal has slightly different env than PM's terminal | M | `subprocess.Popen` without `env=` kwarg inherits PM's env on Windows/Linux. macOS `osascript` runs the spawned Terminal with user's shell env, which usually matches. Document: "spawned agents inherit PM's env except for shell-specific vars." |
| 5 | `start-role.sh` fails silently (bad path, syntax error) and sub-skill thinks spawn succeeded | M | Post-spawn verification: poll `current-state` mtime for 30s. If unchanged, report `spawned=true, verified=false`. Human can investigate. |
| 6 | User explicitly killed agent with `.stop` — sub-skill must not revive | H | `.stop` sentinel check is the FIRST decision rule in §4. Blocks all other conditions. **Critical to test.** |
| 7 | Spawn-spam: agent crashes fast, PM detects every cycle, spawn 20 terminals | M | Rate limiter: `.squidsquad/pm/boot-attempts.log`, skip if attempted within 10 minutes. |
| 8 | Leaking sensitive env vars to spawned terminal (e.g., `SSH_AUTH_SOCK`, `AWS_PROFILE`) | L | Same env as PM already has — no new leakage vector. If user is comfortable with PM having those, they're comfortable with agents having them. |
| 9 | Terminal spam at installer boot time: spawning 5 terminals in rapid succession may trip OS rate limits (macOS dock animations, Windows UAC) | L | Bulk-boot mode inserts a 500ms sleep between spawns. Configurable. |
| 10 | `compose.py` doesn't pick up the new sub-skill file → PM CLAUDE.md doesn't include it | M | Add the entry to `manifest.md` inventory AND to the pm-agent.md / pm-lean.md include lists. Run `compose.py deploy pm` during dev and verify. Add a smoke test that the generated file contains the boot-remote-agents section. |

## 9. Edge Cases

1. **First-time boot (fresh install)**: No `.pid`, no `.stop`, no `current-state`. Sub-skill decision: BOOT. Works as designed — this IS the installer use case.
2. **Agent just context-pressure-exited ~0.5s ago**: `.pid` dead, `current-state` still fresh from pre-exit commit. Decision: SKIP (fresh state wins — wrapper will restart it any second). Helper's 30s "fresh" threshold may need tuning.
3. **Installer bulk-boot of 5 agents at once**: Five near-simultaneous spawns. Mitigation: 500ms stagger. On macOS, Terminal.app may group them in one window depending on prefs. Document and accept.
4. **Linux server / Docker / CI without X11 or tmux**: No spawn mechanism available. `decision=refuse, reason=no-spawner`. Print manual instructions. Sub-skill continues.
5. **WSL with Windows Terminal on PATH**: Detect WSL via `WSL_DISTRO_NAME`. Prefer `wt.exe -w 0 new-tab -- wsl.exe bash -c "..."`. Fallback to tmux inside WSL.
6. **User closes spawned terminal window immediately**: `current-state` never updates, verification fails, sub-skill logs `spawned=true, verified=false`. Acceptable — human has agency.
7. **Remote clone (cross-machine)**: v1 is same-machine ONLY. `.local-config` paths are local. If a path looks remote (contains `:` for drive-only, or starts with `//server/`), `decision=refuse, reason=remote-not-supported`. Future work.
8. **Clone path on a drive that's unmounted**: `os.path.exists(clone_path)` returns False → `decision=refuse, reason=no-clone`. Logged. PM continues.
9. **`start-role.sh` missing (user deleted or unshipped)**: Pre-flight check catches it → `decision=refuse, reason=script-missing`. Discussion comment instructs human to run `compose.py boot-all`.
10. **Concurrent PM upgrade**: `/squidsquad-upgrade` is running and just regenerated `start-role.sh`. File might be momentarily missing mid-write. Mitigation: treat `script-missing` as a soft refuse that retries next cycle, not a hard error.
11. **Two roles share one terminal window** (user's preferred workflow): Not supported — every agent gets its own window. v1 constraint. Document.

## 10. Integration Risks

- **`/squidsquad-upgrade`**: The upgrade flow writes new boot scripts via `compose.py boot-all`. If it runs concurrently with PM's Step 7b, a spawn could target a half-written script. Mitigation: upgrade flow should acquire a lock file `.squidsquad/.upgrading`, and the sub-skill checks for it and defers booting when present. Low-risk in practice (upgrades are rare and fast).
- **npx installer (#269)**: Shipped, but doesn't spawn yet. Q-new21 specifies that `/squidsquad-setup`'s final step will compose this sub-skill as a one-shot bulk boot, then the installer exits. The sub-skill's `--bulk` mode is a future enhancement — v1 can just loop-call `boot_remote.py <role>` N times from the setup prompt.
- **Status bar (`statusline.sh`)**: reads `current-state` content. Currently knows about phases `pulling / testing / idle / etc`. A brief `spawning|Initializing terminal...` state between spawn and first cycle would be nice but isn't critical — the `start-role.sh` wrapper already writes `idle|Initializing...` the moment it runs. So the status bar automatically works for the spawned agent. No changes needed.
- **#320 (role authority)**: The sub-skill lives in `common/` and is composed by PM (and later installer). It reads tracker items to post discussion comments — standard PM-authorized action. No authority concerns.
- **Working-state.md resume**: A spawned agent reads its own `working-state.md` in Step 1c. If the previous session exited mid-task, the spawned agent resumes. No sub-skill involvement needed. Works.
- **#335 (health_check.py)**: Hard blocker. Sub-skill must read from `health_check.py --json` for the authoritative stalled-agent list. Shipping this before #335 would re-introduce #335's bug with amplification.

## 11. Upgrade & Migration

- **New installs (post-#4)**: SKILL.md's setup flow adds `Auto Boot Agents: no` to the default `config.md`. Users can flip to `yes` at any time. PM CLAUDE.md is generated fresh with the new include.
- **Existing installs**: `/squidsquad-upgrade` regenerates all CLAUDE.md files via `compose.py deploy <role>`. The new sub-skill is picked up automatically on next upgrade. Existing configs get the new setting added via `config.py add-setting auto-boot-agents no` (one-shot migration step, part of the upgrade flow).
- **Sub-skill versioning**: Sub-skills aren't independently versioned today — they live in the repo. Upgrades re-run `compose.py` and regenerate all `.squidsquad/*/CLAUDE.md`. If a user has manually edited their CLAUDE.md (against rules), the upgrade will overwrite it. This is the same risk as any other sub-skill update; no new exposure.
- **Backward compat**: If the sub-skill code is present but `config.md` lacks the `Auto Boot Agents` setting, the helper reads it as missing and defaults to `no`. No-op on existing installs. Safe.
- **Rollback**: Remove the include line from `pm-agent.md` + `pm-lean.md` and regenerate. Helper Python file can remain dormant.

## 12. Prior Art

- **#250 (shipped)** — closest pattern. Wrapper loop inside a terminal, handles all the PID/stop/restart logic that #4's sub-skill relies on. #4 is "the next layer up": cross-terminal spawning that trusts #250's wrapper to take over once a terminal exists. Read `FEAT-250-RESEARCH.md` for the full wrapper design; it explains the `.pid`, `.stop`, `current-state`, `restart-log.txt` convention that #4 builds on.
- **#335 (open, blocker)** — the authoritative health check. #4 reads its output.
- **#269 (shipped)** — npx installer research. Shipped without auto-boot by design (see Q-new21). #4 is explicitly the sub-skill the installer will eventually compose for auto-boot.
- **FEAT-SKILL-060** — mentioned cross-platform notifications (`osascript`, `notify-send`, PS toasts). Same OS-detection pattern, good reference for the spawn helper but unrelated feature-wise.
- **FEAT-SKILL-047** — historical bash spawn exploration, grepped for `Start-Process` / `osascript`. Worth skimming during Phase 2 for lessons learned.
- **No prior cross-terminal spawning** in the codebase today. This is a new capability.
- **External patterns**:
  - **LangGraph** / **CrewAI** / **AutoGen** spawn sub-agents as in-process Python objects, not as separate OS terminals. Not analogous — they share a single process. #4's model (one agent = one terminal window) is intentional and unusual, chosen to match the "fresh Claude CLI session per agent" primitive.
  - **tmuxinator / overmind** — same-OS multi-process orchestrators. Similar spirit (declarative "start N processes in N panes") but heavier. We reuse the existing boot scripts instead.
  - **pm2 / forever** (Node ecosystem) — daemonized process management. Not a terminal-spawning model. Not applicable.

## 13. Open Questions for Phase 2 Discussion

1. **Approach A vs B**: Pure-prose sub-skill, or Python helper? Recommending B (matches #335 pattern), but asking for confirmation.
   - *Why it matters*: Determines whether we ship ~0 or ~150 lines of Python, and whether PM can take shortcuts.
2. **Config default**: `Auto Boot Agents: yes` or `no` by default for v1?
   - *Why it matters*: Trust/UX question. `no` is safer (opt-in), but means most users won't benefit until they discover the setting. `yes` is more powerful but spawns terminals without explicit consent.
3. **Terminal preference** on each OS: does v1 ship multi-terminal support (Windows Terminal + cmd + Git Bash; Terminal.app + iTerm; gnome-terminal + konsole + xterm + tmux), or just one per OS with the rest as future work?
   - *Why it matters*: Scope. Multi-terminal = more test surface. Single per OS = simpler but misses power users.
4. **Rate-limiter window**: 10 minutes is a guess. Too short → spam. Too long → stuck agents wait too long for retry. 10m reasonable?
   - *Why it matters*: User-facing behavior under failure.
5. **Bulk-boot mode for installer**: Does v1 include `boot_remote.py --bulk` (spawns all agents in one call) or does the installer loop-call per role?
   - *Why it matters*: Determines whether installer integration is tight or loose. Loose is fine for v1; bulk is a quality-of-life add.
6. **Verification timeout**: 30 seconds to wait for `current-state` freshness after spawn. Reasonable for slow machines? Configurable?
   - *Why it matters*: False-negative rate on "did spawn succeed."
7. **Permission prompt**: On first-use, should PM prompt the human in its check-in step ("I detected skill is stalled. Auto-boot attempt? Reply 'yes' or update Auto Boot Agents in config.")? Or just act silently per config?
   - *Why it matters*: Balance between autonomy and user surprise.
8. **Pre-flight: hardcoded agent list fallback**: If `.local-config` is missing, should the sub-skill refuse entirely, or fall back to scanning sibling directories (`../SquidSquad-2`, `../SquidSquad-3`)?
   - *Why it matters*: Installer use case may not have `.local-config` yet at first boot. Determines whether #4 is strictly blocked on existing config or can bootstrap.
9. **Tracking attempts per-role vs global**: boot-attempts.log keys on role; is that sufficient, or do we need per-clone-path keying for multi-project users?
   - *Why it matters*: Edge case for users running multiple SquidSquad installs on one machine.
10. **WSL handling**: Treat as Windows (launch `wt.exe`) or Linux (launch `tmux`)?
    - *Why it matters*: Affects a growing user cohort; wrong default makes WSL experience bad.
11. **Shipping without #335**: Can we un-block and ship a v0 that trusts the prose health check, or do we gate strictly on #335?
    - *Why it matters*: Dependency chain. Recommendation: **strict gate**, but PM may have reasons to decouple.
12. **Sub-skill as common/ vs pm-specific/**: The design note says "common" (so installer can compose it too). But in v1 only PM uses it. Does common still make sense, or does it start in pm-specific/ and graduate?
    - *Why it matters*: Directory hygiene. Installer composition is the stated reason for `common/`; if installer work is 2-3 cycles away, "premature common" is fine.

## 14. Recommendation

**Feasible with caveats.**

The feature is well-understood, bounded in scope, and built on top of existing primitives (#250's wrapper, upcoming #335's health check, `.local-config`'s path map, `start-role.sh`'s PID lock + stop sentinel). The Python helper approach (§2B) is the right shape — mirrors #335, avoids prose drift, cleanly unit-testable.

**Caveats**:

1. **Hard dependency on #335**: Do not ship #4 before `health_check.py` lands. Auto-boot driven by unreliable health data is worse than no auto-boot — it actively damages trust. Phase 2 should explicitly lock the ordering.
2. **Config gate default to `no`**: For v1, the feature should be opt-in. Most users installing v1.0 of SquidSquad will never have touched it; suddenly spawning terminals on their desktop is startling. The installer's Q-new21 follow-up can flip it to `yes` in fresh-install config, with a clear setup prompt ("Should PM auto-boot missing teammates? [Y/n]").
3. **Scope discipline on terminal support**: v1 targets one terminal per OS (Windows Terminal on Win, Terminal.app on macOS, gnome-terminal+tmux fallback on Linux+WSL). Additional emulators are follow-ups filed as low-priority improvements.
4. **Rate limiting is mandatory, not optional**: Without it, a crashing agent generates N spawn storms per hour. The `boot-attempts.log` + 10min cooldown should ship with v1, not v2.
5. **Post-spawn verification must not block PM**: The 30-second current-state poll must be non-blocking from PM's perspective — PM can fire the spawn, continue to other steps, and check verification later (or let the next cycle's health check handle it). Otherwise a slow-boot agent delays PM's whole cycle by 30s × N roles.

Estimated total effort (Phase 2-5): medium. ~200 lines of code, ~1-2 days of dev + test time on the sub-skill and helper. OS-specific manual testing is the biggest time sink and should be explicitly budgeted.
