# FEAT-1 Context — Templatize Boot Scripts (start-*.ps1 / start-*.sh)

## Scope

Replace 6 separate boot scripts (3 .ps1 + 3 .sh) with a single template per platform, parameterized by role. A `compose.py boot` subcommand generates role-specific scripts from templates. Also fix existing drift bugs and update SKILL.md setup templates.

**Delivers:**
1. `references/templates/start.ps1.template` — PowerShell boot script template
2. `references/templates/start.sh.template` — Bash boot script template
3. `compose.py boot` subcommand — generates `start-[role].ps1` and `start-[role].sh` from templates
4. Fix existing drift: `start-skill.ps1` missing safety guards, inconsistent init messages
5. Update SKILL.md setup flow to use `compose.py boot` instead of inline templates
6. Generated scripts include DO NOT EDIT header

## Locked Decisions (human decided)

- **Init message standardized**: All roles use "start the loop". No role-specific prefix. Template has exactly 1 parameter: ROLE. Why: the role prefix is redundant (SQUIDSQUAD_ROLE already identifies the agent), and fewer parameters means simpler template.

- **DO NOT EDIT header**: Yes, same pattern as CLAUDE.md. First line: `# GENERATED by compose.py boot [role]. DO NOT EDIT.` (or PS1 equivalent). Why: consistent with CLAUDE.md convention, prevents accidental edits that get overwritten.

- **Single template for all roles**: One .ps1.template and one .sh.template serve all roles (skill, pm, dm, and future fe/be/designer/qa). Why: research proves all roles differ only by the ROLE placeholder. Separate templates recreate the drift problem.

- **Conditional permissions execution**: `[ -x .squidsquad/inject-permissions.sh ] && bash .squidsquad/inject-permissions.sh` — skips cleanly if missing, errors visible if broken. Why: not all setups need inject-permissions.sh; hiding errors (2>/dev/null) masks real problems.

## Dev Discretion (dev agent can choose)

- Template syntax (Jinja2, simple string replacement, or compose.py's existing `{{ROLE}}` pattern)
- Whether `compose.py boot` generates all roles at once or takes a role argument
- How to handle the BOM marker on PS1 files (include in template or add during generation)
- Line ending handling (CRLF for .ps1, LF for .sh — enforce during generation or leave to git)
- Whether to add `compose.py boot` as part of `compose.py deploy` or keep it separate

## Side Effect Mitigations (required)

- **Existing scripts**: Generation overwrites existing boot scripts. The DO NOT EDIT header warns users. If a user has custom modifications, they'll need to re-apply them after generation (document this in upgrade notes).
- **Setup flow**: SKILL.md Step 5 (lines 595-933) contains inline boot script templates that are outdated (missing --name flag). These MUST be replaced with a `compose.py boot` invocation.
- **Test compatibility**: All 51 existing start script tests (test_start_scripts.py) must pass on generated output. Tests validate the generated files, not the templates.
- **Permissions**: Generated .sh files must be `chmod +x`. The generation script handles this.
- **Manifest**: Update `references/sub-skills/manifest.md` if boot scripts are referenced there.

## Upgrade Path (required)

- **New files**: `references/templates/start.ps1.template`, `references/templates/start.sh.template`
- **Modified files**: `references/scripts/compose.py` (add boot subcommand), SKILL.md (replace inline templates with compose.py boot call)
- **Regenerate**: Run `compose.py boot` for all configured roles to replace existing scripts
- **Graceful degradation**: Non-upgraded installs keep their existing hand-written scripts. No breakage.
- **Migration**: `/squidsquad-upgrade` should run `compose.py boot` to regenerate scripts from templates

## Out of Scope

- Custom per-role boot logic beyond the ROLE parameter
- Boot script for non-Claude-Code platforms
- Hot-reload of boot scripts (they run once at agent start)
- Boot script testing on actual agent startup (covered by existing 51 tests on file content)
