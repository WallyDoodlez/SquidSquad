### Finding 1

- **File**: references/scripts/compose.py
- **Line**: 1260 (and the path through deploy_role at 1184)
- **Severity**: warning
- **Issue**: Unsanitized alias value used directly in filesystem path construction — path-traversal risk.
- **Evidence**: `deploy_alias_v2` passes the alias to `deploy_role` as `output_name=alias` (line 1260). In `deploy_role`, `output_name` is placed directly into a `Path` at line 1184: `target_root / ".squidsquad" / output_name / output_filename`. The `parse_aliases_registry()` parser in config.py validates that `role_class` is in `ALIASES_ROLE_CLASSES` (line 412) and that the alias cell is non-empty (line 402), but performs **no character validation** on the alias value itself. An alias like `../../../tmp/evil` would produce a path that resolves outside `.squidsquad/`, and `output_path.parent.mkdir(parents=True, exist_ok=True)` (line 1185) would create the attacker-specified directory tree. Additionally, the subsequent `output.relative_to(REPO_ROOT)` call at line 1632 would raise `ValueError` (since the path escapes the repo root), turning a covert write into a loud crash — but only *after* the file has been written.

  **Mitigating factor**: exploitation requires editing `.squidsquad/config.md` (admin-level access to the repo). However, defense-in-depth in a code-generation pipeline should still validate or sanitize path components derived from human-editable config.
- **Suggested fix**: In `deploy_alias_v2`, validate the alias against a safe pattern before passing it to `deploy_role`. For example:
  ```python
  import re
  if not re.match(r'^[a-zA-Z0-9][-a-zA-Z0-9_]*$', alias):
      print(f"ERROR: alias '{alias}' contains disallowed characters.", file=sys.stderr)
      sys.exit(1)
  ```
  Or alternatively, in `deploy_role` itself, resolve `output_name` and verify it doesn't escape the target directory: `if ".." in output_name or output_name.startswith("/"): raise ValueError(...)`.

- **Evidence**: The `--v2` flag is stripped unconditionally at lines 1612-1613 before `cmd` is dispatched. The user receives no warning that `--v2` was ignored. While the AC states `--v2` is "recognized on `deploy` and `deploy-all`," silently discarding the flag on other commands is a confusing UX — a user who runs `compose.py all --v2` would reasonably expect something different from `compose.py all`.
- **Suggested fix**: After the dispatch, or in a post-dispatch check, warn if `v2_mode` is `True` but the command was not `deploy` or `deploy-all`:
  ```python
  if v2_mode and cmd not in ("deploy", "deploy-all"):
      print("WARNING: --v2 flag has no effect on this command.", file=sys.stderr)
  ```
  Or reject with `sys.exit(1)` and a "not supported" message, depending on the desired strictness.

- **Issue**: The generated v2 output file header contains an incorrect regeneration instruction that would produce different output if followed.
- **Evidence**: In `deploy_role` (lines 1181-1182), the file header is generated as:
  ```python
  header += f"<!-- GENERATED by compose.py deploy {role_name}. DO NOT EDIT. -->\n"
  header += f"<!-- Regenerate: python references/scripts/compose.py deploy {role_name} -->\n\n"
  ```

  When called from `deploy_alias_v2` with `role_name="worker"` and `output_name="frontend-1"` (line 1258-1262), the resulting file at `.squidsquad/frontend-1/CLAUDE.linked.v2.md` will contain:

     ```python
     # in deploy_role signature
     regenerate_cmd: str = None
     ...
     cmd_display = regenerate_cmd if regenerate_cmd else role_name
     header += f"<!-- Regenerate: python references/scripts/compose.py deploy {cmd_display} -->\n\n"
     ```
     And in `deploy_alias_v2`, pass `regenerate_cmd=f"{alias} --v2"`.

### Finding 5

- **File**: references/scripts/compose.py
- **Line**: 1659 (and 1237 inside `deploy_alias_v2`)
- **Severity**: warning
- **Issue**: `deploy-all --v2` parses the aliases registry twice per alias — once in `main()` to iterate and once inside `deploy_alias_v2()` to resolve — causing redundant disk I/O and a TOCTOU window.
- **Evidence**: At line 1659, `main()` calls `_config_module.parse_aliases_registry()` to get the list of aliases to iterate. Then for each alias in the loop (line 1664), it calls `deploy_alias_v2(alias)`, which at line 1237 calls `_config_module.parse_aliases_registry()` again. For N aliases, this is N+1 parses of the same file. More importantly, if `config.md` is modified between the loop's registry parse and `deploy_alias_v2`'s internal parse (e.g., by a concurrent process), the alias could disappear from the second parse, causing an unexpected `SystemExit(1)` even though the alias was valid at iteration start.
- **Suggested fix**: Have `deploy_alias_v2` accept an optional pre-parsed `registry` argument so `deploy-all` can pass the registry it already has:
  ```python
  def deploy_alias_v2(alias, registry=None):
      if registry is None:
          registry = _config_module.parse_aliases_registry()
      ...
  ```
  And in `main()` for `deploy-all --v2`, pass `registry=registry`.
