# FEAT-PM-2495 Research — Rewrite /squidsquad-upgrade Instructions in SKILL.md

## Summary

The current `/squidsquad-upgrade` instructions in `SKILL.md` (lines 326–379) describe a 5-step fan-out pattern using parallel subagents that each manually regenerate templates, boot scripts, and settings by reading from `references/agent-instructions.md` and substituting placeholders. This entire description is architecturally obsolete: `references/agent-instructions.md` is now a generated intermediate artifact (not the source of agent templates), placeholder substitution is handled by `compose.py deploy-all`, boot scripts are generated by `compose.py boot-all`, and the v2 config schema has many new sections the upgrade step never mentions. The `.claude/commands/squidsquad-upgrade.md` skill file is also stale — it still references `references/agent-instructions.md` as the template source and a non-existent `Tracker Schema` field in `config.md`.

The recommended rewrite replaces the obsolete parallel-subagent fan-out with a concise orchestrator-only flow: load `.squidsquad/.install-spec.json` (if present), run `python references/scripts/compose.py deploy-all && boot-all`, detect and patch missing config.md sections against the v2 schema defined in `wizard.py`'s `build_config_md`, and commit. The `.claude/commands/squidsquad-upgrade.md` skill file must also be updated in sync — the skill invokes the prose instructions, so they must agree. SOUL.md files are the primary user-customized artifact and must never be touched by upgrade; the upgrade flow in `compose.py deploy_role` already enforces this by only writing SOUL.md when missing.

Primary risks are: (1) the config schema gap between the v1 schema currently in `.squidsquad/config.md` (`Architecture Version: 1`) and the v2 schema produced by `wizard.py build_config_md` — sections like `## Preset`, `## Agents` (new format), `## Tools`, `## Flags`, `## Forge Backend`, `## Model Routing`, `## Git Branches` may be missing in old installs; (2) the `.install-spec.json` file, which `wizard.py` started writing at install time, does not exist in the current dogfood repo (this install predates the feature), so upgrade must handle the no-spec path gracefully; (3) clone isolation means each agent's CLAUDE.md lives in a separate git clone, and deploy-all only touches the primary repo — the upgrade instructions must note that agents pull the new CLAUDE.md on their next git pull, not via a cross-clone write.

## Side Effects

- **Risk 1: SOUL.md preservation** — `compose.py deploy_role` already protects SOUL.md (only writes when missing). The new instructions should explicitly confirm this guarantee so users aren't worried. Severity: **Low** — mitigated by existing code; no change needed.

- **Risk 2: Config schema v1 → v2 gap** — The live dogfood `config.md` has `Architecture Version: 1` and is missing many v2 sections (`## Preset`, `## Flags`, `## Tools`, `## Forge Backend` in new format, etc.). The upgrade step must detect missing sections and add them with safe defaults, not overwrite the entire file. Severity: **High** — if unaddressed, agents reading config fields that don't exist will get empty/error results. Mitigation: upgrade reads each expected section header; if absent, appends it with a documented default.

- **Risk 3: No `.install-spec.json`** — Old installs (including the SquidSquad dogfood repo itself) will not have `.squidsquad/.install-spec.json`. Severity: **Medium** — if the upgrade tries to load it unconditionally, it will error. Mitigation: make the spec load optional; if absent, derive agent list from `config.md`'s `## Agents` section (which is present) and proceed with deploy-all.

- **Risk 4: Clone isolation — other agent clones** — `compose.py deploy-all` writes into `.squidsquad/<role>/CLAUDE.md` in the primary repo only. Non-PM agents run in sibling clones (`../SquidSquad-skill`, etc.) and pull the primary repo's git history via their `origin` remote. Their CLAUDE.md updates arrive on next `git pull`. The upgrade instructions must note this: after committing the deploy-all output, agents get updated templates on their next cycle pull, not immediately. Severity: **Low** — informational gap only, no data loss.

- **Risk 5: Heartbeat section removal** — Current instructions say to remove `## Heartbeat` from config.md if present (it was replaced in v0.8.0+). The live dogfood config does not have this section, so the check is a no-op here. But for external users on old installs it may still matter. Keep this migration step. Severity: **Low**.

- **Risk 6: `.squidsquad/templates/` creation** — Current instructions say to create this if it doesn't exist. The live dogfood repo has no `.squidsquad/templates/` directory. The new compose.py flow doesn't use this directory — it writes directly to `.squidsquad/<role>/CLAUDE.md`. This note can be dropped from the rewrite. Severity: **Low** — the note is obsolete.

## Edge Cases

- **Already up to date**: Both versions match — skip all work, report up-to-date. Covered.
- **No `install-spec.json`**: Fall back to reading agent list from `config.md` `## Agents` section. The `dev-agents` config.py field (comma-separated) provides the dev agent list; PM is always present; DM if `.squidsquad/dm/` exists.
- **Config.md is v2 already** (`Architecture Version: 2`): All sections present — the section-patching loop is a no-op. Safe.
- **Config.md has no `Architecture Version` field**: Treat as v1 (old install). Apply all v1→v2 patches.
- **DM not installed**: `compose.py deploy-all` already checks for `.squidsquad/dm/` before including DM. Covered.
- **designer agent present**: `compose.py deploy-all` reads dev-agents from config (which may include `designer`). Covered.
- **Inline Ralph Loop CLAUDE.md (pre-bootstrapper)**: The old instructions described detecting this via line count. This check is no longer needed — `compose.py deploy_role` always overwrites CLAUDE.md (the header says `DO NOT EDIT`). The SOUL.md is the only protected file. Drop this detection step from the new instructions.
- **Windows paths in boot scripts**: `compose.py boot_role` already handles `.sh` (LF line endings) and `.ps1` (UTF-8 BOM) natively. No special casing needed in upgrade instructions.

The config-patching step should add these with defaults (`yes` for branch-workflow, `yes` for auto-merge) so agents don't break.

The upgrade skill currently tells subagents to read it as the source of templates — this is wrong. The actual sources are `references/roles/<role>/CLAUDE.md` entry files. The rewrite must remove all references to reading `agent-instructions.md` for template content.

- **`squidsquad-setup` skill**: The setup flow in `.claude/commands/squidsquad-setup.md` follows the same `compose.py deploy-all` path. If someone upgrades and then runs setup again, it should be idempotent (SOUL.md protected, config.md patched, not overwritten). Verify no conflicts.

## Upgrade & Migration (meta)

This task is itself instructions for the upgrade skill. The question of how the upgrade skill upgrades itself is answered by the delivery mechanism: when this SKILL.md change is shipped, agents receive the new `SKILL.md` on their next git pull. The `squidsquad-upgrade.md` skill file in `.claude/commands/` is also updated in the same commit. Neither file is generated by compose.py — they are hand-maintained. Therefore, the meta-upgrade path is simply: commit the new instructions to git, push, and agents pick them up normally. No special self-upgrade logic is required.

The v1→v2 config schema upgrade that the new instructions describe will handle existing installs (including the SquidSquad dogfood repo, which is currently at `Architecture Version: 1`). The key new sections to patch in are:

- `## Preset` (with `- **Id**: software-dev` default)
- `## Agents` in v2 format (with `role`, `variant`, `test_command` sub-fields per agent)
- `## Tools` (initially empty or `- (none)`)
- `## Flags` (with current booleans from existing sections like `## PR Flow`, `## Branch Workflow`, `## Improvement Scanning`, etc.)
- `## Forge Backend` (if not present — Provider: github, Endpoint: https://api.github.com)
- Normalize `## Model Routing` if present (add any missing model fields)
- Set `Architecture Version: 2` after patching

**Critical**: the existing old-format sections (`## PR Flow`, `## Branch Workflow`, `## Auto Merge`, `## Vault Optimize`, `## Vault Remember`, `## Improvement Scanning`, `## Cycle Runner`, `## Diagnostics`) should NOT be deleted during v1→v2 migration because agents currently read them via `config.py get` using the old field names. Only add the new v2 sections alongside; do not strip the old ones until a separate migration task explicitly handles config reader compatibility.

## Open Questions

- **Q1**: Should the upgrade skill update `Architecture Version` to `2` in `config.md`? — **Why**: If it does, scripts that might later check this field will behave correctly; but the current `config.py` reader doesn't read this field, so there is no immediate breakage either way. Recommendation: set it, since it signals the schema level for future tooling.

- **Q2**: Should the upgrade skill handle the case where `compose.py deploy-all` fails for one role (e.g., references/roles/<role>/CLAUDE.md is missing for a custom role)? — **Why**: External users may have custom role names not in `references/roles/`. `compose.py` falls back to `dev` role template for unknown names, so this should work. No special handling needed.

- **Q3**: The current `squidsquad-upgrade.md` skill checks for `Tracker Schema` in config.md. This field does not exist. Should the rewritten skill still check tracker migration, or drop it entirely? — **Why**: The tracker has been `github-issues` since v0.10.0 and there is no schema field to read. Recommendation: drop the tracker schema check; the `## Schema Changelog` section in SKILL.md already documents historical migrations and is for reference only.

- **Q4**: Should the new upgrade instructions mention `wizard.py ensure-labels` to sync any new GitHub labels? — **Why**: New SquidSquad versions may add new tracker labels (e.g., `design:*` labels were added in a recent version). Calling `wizard.py ensure-labels` is idempotent and catches this. Recommendation: include as an optional step with a note that it is safe to re-run.

## Recommendation

**Feasible with caveats.**

The core rewrite is straightforward: replace the manual fan-out instructions with `compose.py deploy-all` + `compose.py boot-all`, drop the obsolete inline-Ralph-Loop migration detection, and update `.claude/commands/squidsquad-upgrade.md` to match. The caveats are:

1. The config v1→v2 schema patching is non-trivial to specify correctly: the instructions must be precise about which sections to add and what defaults to use, without destroying the existing sections that `config.py` readers still depend on.
2. The no-install-spec fallback path must be explicit.
3. Both `SKILL.md` and `.claude/commands/squidsquad-upgrade.md` must be updated atomically — they are two surfaces of the same behavior and must agree.

No new scripts are required. All mechanical operations (compose, boot, config reading) are already implemented. This is a documentation/instructions rewrite with a config-patching prose step.
