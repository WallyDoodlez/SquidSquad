# FEAT-SKILL-918 Research -- Self-Restart Mechanism

## Summary

The self-restart mechanism is **already fully implemented** across all layers of the SquidSquad stack. This research found no capability gap -- the sentinel-based restart was designed, coded, and deployed as part of an earlier effort. The issue title "Agents cannot self-restart -- no mechanism to exit or reboot" is **outdated**; the mechanism exists and is wired into every agent role.

**What exists today:**

1. **Sub-skill**: `references/sub-skills/common/self-restart.md` -- documents the sentinel protocol, safety rules, and restart triggers (context pressure, template change).
2. **Boot script support (both platforms)**: `references/templates/start-role.sh` (lines 48, 124-134) and `start-role.ps1` (lines 55, 109-119) both define `RESTART_SENTINEL="$ROLE_DIR/.restart"` and check for it after each Claude exit. On detection: read reason, delete sentinel, log to `restart-log.txt`, reset backoff counter, sleep 2s, continue loop.
3. **Composition**: All 5 role templates include `{{include: common/self-restart}}` -- dev, pm, qa, dm, designer. Confirmed via both `CLAUDE.md` entry files and `includes.yml` manifests.
4. **Context pressure integration**: `references/sub-skills/common/context-pressure.md` sets a flag when threshold exceeded, which the self-restart sub-skill checks at cycle end (Step Done).
5. **Real usage**: `.squidsquad/skill/restart-log.txt` shows at least one restart event (`2026-04-11 23:50:20 | exit=0 | restart=1 | runtime=82373s`), confirming the wrapper loop works.

### What would break if changed

Nothing needs changing. The mechanism is complete. If modifications were proposed:
- Changing the sentinel filename would require updating templates + sub-skill + all generated boot scripts.
- Adding sentinel content schema would require sub-skill update and template parsing changes.
- Changing timing (the 2s sleep after sentinel detection) affects all roles.

## Side Effects

### Sentinel left behind after crash

**Risk**: If the agent crashes AFTER writing `.restart` but BEFORE Claude exits, the boot script will still detect it on the next loop iteration and treat it as a self-restart. This is **correct behavior** -- the agent wanted to restart, and the crash just accelerated the exit.

**Risk**: If the agent crashes BEFORE completing the pre-restart checklist (commit, push, save working state) but AFTER writing `.restart`, the restart will happen but working state may be incomplete. The sub-skill mitigates this by requiring the checklist BEFORE writing the sentinel (self-restart.md lines 12-15). Since Claude writes files sequentially, the sentinel write is the last action.

**Risk**: If the boot script crashes between reading and deleting the sentinel, the next iteration would see it again. The `rm -f` (bash) / `Remove-Item -ErrorAction SilentlyContinue` (ps1) is the first operation after detection, minimizing this window.

### Two agents writing .restart simultaneously

**Not a real concern.** Each agent has its own `.squidsquad/{role}/.restart` file in its own role directory. Two agents (e.g., pm and skill) writing their respective sentinels simultaneously is completely safe -- no shared file. Even in a single-clone setup where all agents share the same repo, each role's directory is isolated.

### Windows file locking

**Low risk.** The sentinel file is tiny (one line of text). The boot script reads then deletes. PowerShell's `Get-Content` followed by `Remove-Item` does not hold locks between operations. The `Set-Content` write from Claude is atomic enough for a single-line file. No concurrent readers/writers exist for the same role's sentinel (one Claude process per role, one wrapper per role).

The `current-state` file has a more sophisticated atomic write pattern (`.tmp` + `mv`) because the statusline script reads it concurrently. The `.restart` sentinel does not need this -- only the boot script reads it, and only after Claude exits.

## Edge Cases

### 1. Agent crashes before deleting sentinel (infinite restart loop?)

**Not possible as designed.** The BOOT SCRIPT deletes the sentinel, not the agent. Flow:
1. Agent writes `.restart`
2. Agent exits (or crashes)
3. Boot script detects `.restart`, reads reason, DELETES it, logs, restarts

The sentinel is always cleaned up by the wrapper. The only infinite loop risk would be if the agent immediately writes `.restart` again on the next session. The sub-skill guards against this: "Maximum 3 self-restarts per hour (tracked in restart-log.txt). If exceeded, skip the restart and print a warning."

### 2. Shell script polls while Claude is mid-write

**Not possible.** The shell script only checks for the sentinel AFTER `wait $CHILD_PID` returns (bash) or after the `claude` command exits (ps1). The check happens between Claude sessions, never during one.

### 3. .restart written but working state not saved yet

Addressed by the pre-restart checklist in self-restart.md: "Never write `.restart` if working state has uncommitted changes -- commit first." The sentinel write is the LAST step. If the agent violates this order, the worst case is a restart with stale working state -- the agent resumes from the last committed state, losing at most one cycle's uncommitted work.

### 4. Restart counter overflow

The boot script resets `RESTART_COUNT=0` on self-restart detection (line 132 in template). This is correct -- self-restarts are intentional, not crash loops. The 50-restart max only applies to unintentional exits.

### 5. Template upgrade during active session

The self-restart sub-skill detects CLAUDE.md mtime changes. But the BOOT SCRIPT template changes are NOT detected this way -- boot scripts are only regenerated by `compose.py boot {role}`. An agent running an old boot script without sentinel support would ignore the `.restart` file. See Upgrade & Migration below.

## Integration Risks

### health_check.py

**No conflict.** Health check reads `current-state` mtime to determine staleness. During a self-restart:
1. Agent writes "restarting|Self-restart..." to current-state
2. Boot script writes "restarting|Self-restart: [reason]" to current-state
3. Boot script writes "idle|Initializing..." on next loop

The 2s sleep between sentinel detection and restart means health_check might briefly see "restarting" state. This is correctly categorized as HEALTHY (mtime is recent).

### boot_remote.py

**No conflict.** boot_remote.py checks `.stop` sentinel to skip stopped agents (line 167-168 in `_needs_boot`). It does NOT check `.restart` -- correct, because `.restart` is transient (written then deleted within seconds). If health_check reports an agent as "stalled" during the 2s restart window, boot_remote would attempt to boot it, but:
1. The grace period check (`_check_grace_period`, 120s) would likely prevent double-spawn.
2. The PID lock in the boot script prevents double-start.
3. The boot-lock file prevents concurrent boot_remote operations.

### PID lock mechanism

**Compatible.** The boot script's PID lock (`$ROLE_DIR/.pid`) is managed by the wrapper, not Claude. On self-restart:
1. Wrapper holds the PID lock throughout
2. Old Claude child exits
3. Wrapper starts new Claude child
4. PID lock ($$ = wrapper PID) never changes

No PID lock conflict possible.

### .stop sentinel

**Complementary.** `.stop` prevents restart entirely (boot script breaks out of the while loop). `.restart` requests immediate restart (boot script continues the loop). If both exist simultaneously, `.stop` is checked FIRST (lines 116-121 in template), so `.stop` wins. This is the correct priority -- explicit stop overrides self-restart.

## Upgrade & Migration

### Boot script regeneration

Agents running OLD boot scripts (generated before sentinel support was added) will NOT detect `.restart` files. The agent will write the sentinel, exit normally, and the old wrapper will treat it as a regular exit (10s cooldown for healthy runs, exponential backoff for fast crashes). The sentinel file will persist on disk until manually deleted or the boot script is regenerated.

**Migration path**: Run `python references/scripts/compose.py boot-all` to regenerate all boot scripts. This is safe to run while agents are stopped. Running it while agents are active requires restarting the wrapper scripts manually (the scripts are not hot-reloaded).

### CLAUDE.md template updates

The sub-skill is composed into CLAUDE.md via `compose.py deploy {role}`. Agents pick up CLAUDE.md changes on restart (the instructions are read at session start via `--append-system-prompt "SQUIDSQUAD_ROLE={role}"`). The self-restart sub-skill itself detects CLAUDE.md mtime changes and triggers a restart to pick up the new instructions. This is self-bootstrapping -- once an agent has the self-restart sub-skill, it can detect and apply future template changes.

### compose.py awareness

`compose.py boot_role()` (line 421-441) reads from `references/templates/start-role.{sh,ps1}` and substitutes `{{ROLE}}`. The sentinel logic lives in the template, not in compose.py. No compose.py changes needed for the sentinel mechanism.

## Capability Gaps

### capability_check.py results

```
$ python references/scripts/capability_check.py skill
ERROR: Role manifest not found (skill has no manifest.yaml -- dev variant)

$ python references/scripts/capability_check.py dev
OK: dev requires no capabilities.
```

The dev role (and its variants like skill) require no external capabilities. Self-restart is a builtin mechanism (file write + shell script detection), not an MCP/CLI/HTTP capability.

### Actual gap: Claude has no "exit" tool

The fundamental issue described in #918 is that Claude cannot programmatically exit a conversation. The sentinel mechanism works AROUND this:
- Claude writes `.restart`, then the conversation naturally ends (context exhaustion, /loop cycle completion, or the shell kills it).
- Claude cannot force-exit itself, but it can SIGNAL that it wants to restart.

**This is a Claude platform limitation, not a SquidSquad gap.** The sentinel approach is the correct workaround. The `/loop` command's cycle-based execution model means Claude finishes a cycle and returns, at which point the wrapper detects the sentinel.

### Gap: No rate-limit enforcement in the agent

The sub-skill says "Maximum 3 self-restarts per hour (tracked in restart-log.txt)." But the enforcement is on the AGENT side (reading the log file and deciding not to write the sentinel). A misbehaving agent could ignore this. The boot script itself has no per-hour rate limit -- it only has the `MAX_RESTARTS=50` total counter and the exponential backoff for fast crashes. Self-restarts reset the counter to 0.

**Recommendation**: Add a shell-side rate limit for self-restarts. Example: in the sentinel detection block, count self-restart entries in the last hour from restart-log.txt and refuse to restart if > 3.

## Open Questions

1. **Is #918 actually about a different problem?** The sentinel mechanism exists and is deployed. Is the issue that agents are not USING it (e.g., not writing the sentinel at context pressure threshold)? Or is there a specific scenario where the mechanism fails?

2. **Should the boot script enforce the 3/hour rate limit?** Currently only the agent sub-skill enforces it. Adding shell-side enforcement would be a defense-in-depth improvement.

3. **Should `.restart` support structured reasons?** Currently it's a single line of text. A structured format (JSON or key=value) could enable the boot script to take different actions (e.g., `reason=template-change` could trigger `compose.py deploy` before restart).

4. **Windows signal handling**: The PowerShell template does not have SIGINT/SIGTERM trap equivalents for the inner Claude process. On Windows, Ctrl+C behavior depends on the terminal. Is this causing restart issues on Windows specifically?

## Recommendation

**Close #918 as already-implemented**, or re-scope it to one of these narrow follow-ups:

1. **Shell-side rate limiting** (small): Add 3/hour self-restart limit in the boot script template, not just agent-side. Prevents runaway restart loops from misbehaving agents.

2. **Verification that agents actually trigger self-restart** (investigation): Check if context pressure actually causes agents to write the sentinel in practice. The restart-log.txt for the skill role shows only 1 entry and it was a normal restart (not self-restart), suggesting agents may not be reaching the self-restart code path.

3. **Structured sentinel content** (enhancement): Allow the sentinel to carry metadata that the boot script can act on (e.g., run compose.py deploy before restarting).

The core mechanism -- sentinel file, boot script detection, sub-skill instructions, composition into all roles -- is complete and operational.
