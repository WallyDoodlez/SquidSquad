# AUDIT-A-events-architecture Research — Comprehensive Architectural Audit of SquidSquad's Event-Driven Mode

## Summary

Researched the entire event-driven architecture across `harness.py` (lines 486–2566), `event_poll.py`, `event_bus.py`, `event_bus_reader.py`, `event_catalog.py`, `event_validator.py`, `compose.py`, `cycle_pre.py`, `cycle_post.py`, `tracker.py`, `boot-bootstrap.md`, and the six `common-events/*.md` fragments (l1-base, cursor-management, forge-read-pattern, idle-cooldown-loop, comment-handling, pr-merge-wait). No BLOCKER-level finding was identified; the current architecture is shippable but would benefit from targeted hardening of the gaps below.

## Side Effects

- **Risk 1: Cursor re-anchor / per-event advance race** — **Severity: MEDIUM** — In `event_poll.py:222-258`, the eviction-gap handler re-anchors the cursor to `oldest_id` before processing events, then per-event advances overwrite it. If the re-anchor write succeeds but a subsequent per-event cursor write fails (disk full/permission), the cursor stays at `oldest_id` and the agent has silently consumed the re-anchor event (which holds `oldest_id`) without emitting it to stdout. The function returns None (fatal), but on retry, `since=oldest_id` finds that id in the deque and skips it — one event is permanently lost. **Mitigation**: Move the re-anchor write to AFTER the per-event loop, writing `oldest_id` only if no events were processed (the batch was all-filtered case). Or, equivalently, only re-anchor when the events list is empty. This preserves the "re-anchor up front for forward progress" intent (the comment at line 214-221 explains why) while avoiding the lost-event path.

- **Risk 2: `GET /events/for/{role}` dispatch with no consumer** — **Severity: MEDIUM** — `harness.py:1674-1678` calls `event_lifecycle.dispatch()` for each event delivered via the targeted endpoint. `dispatch()` marks events in-flight and persists to `.event-state.json`. The timeout scanner (`harness.py:742-788`) runs every 30s and logs timeouts after 10 minutes. But the agent never sends an ack (the agent contract never mentions acking in l1-base.md or event-driven-workflow.md — the agent only advances the cursor). This means every event delivered via `/events/for/{role}` will eventually timeout, creating log spam and growing `.event-state.json` with in-flight/dispatched entries that are never cleaned up. The `_persist()` method (line 665-686) writes these to disk on every dispatch. **Mitigation**: Either document that in-flight tracking is intentionally dormant (Phase 4 deferred), or add a cursor-advance-as-implicit-ack pattern where `event_poll.py` also POSTs an ack after advancing, or strip the `dispatch()` call from the endpoint until the full lifecycle is wired.

- **Risk 3: `_update_agent_from_event` trusts event payloads for AgentState** — **Severity: LOW** — `harness.py:1391-1412` updates AgentState fields (`current_cycle`, `last_cycle_start`, `last_cycle_end`, `last_cycle_type`, `current_phase`) directly from event payloads without any forge verification. This is by design (the harness is a broadcast pipe, these are informational dashboard fields), but it means a misbehaving mechanical script (or a bug in `event_bus.emit()`) can inject arbitrary values into the harness's agent state. These values are surfaced via `GET /agents/{role}` and `GET /status`. **Mitigation**: Document the trust boundary explicitly: the harness trusts its own agents' event payloads for informational fields; if this ever drives automated decisions (e.g., auto-reboot on "agent seems stuck based on last_cycle_start"), add sanity bounds.

- **Risk 4: Boot-time harness reachability TOCTOU** — **Severity: MEDIUM** — `boot-bootstrap.md` Step 2 probes harness reachability via `curl -sf --max-time 5`. If reachable, the agent enters event mode and reads the l1-base fragment, which says "Harness reachability is guaranteed by the bootstrap (#9588)." But there is a TOCTOU window: the harness could go down between the curl check and the agent starting `event_poll.py`. In this window, l1-base says "do NOT pivot to forge-direct work mid-session" and "operator restarts the agent to recover." The result is a hung session that requires manual intervention. **Mitigation**: In `event_poll.py`'s main loop, if the harness becomes unreachable (the `--wait` loop's poll returns None), exit non-zero so the thin launcher or harness auto-reboot catches it, rather than hanging forever. Currently the `--wait` loop at line 307-310 exits on poll returning None with `sys.exit(2)` — which is correct. But the agent's Monitor tool wrapping `event_poll.py` would see the tool exit, not a hanging stream. The l1-base fragment should clarify that if the Monitor tool exits (event_poll.py dies), the agent should not attempt manual recovery but should exit the session.

- **Risk 5: Improvement-scan mid-scan event delivery semantics** — **Severity: MEDIUM** — `idle-cooldown-loop.md` specifies "An event arrives during an in-flight scan → finish the scan first (atomicity rule)." But in the Monitor streaming model, `event_poll.py` delivers events to stdout as JSON lines. If the agent is mid-scan (running a tool), the Monitor output is buffered and the cursor has already been advanced by `event_poll.py`. When the agent finishes the scan and reads the buffered Monitor output, the event's cursor position is already consumed. If the agent crashes between the cursor advance and processing the buffered event, that event is lost (cursor already past it). This is a consequence of the "per-event advance" design interacting with tool execution that doesn't read Monitor output. **Mitigation**: The idle-cooldown-loop fragment should explicitly state that during a scan, Monitor output lines are buffered by the Claude Code runtime, and the agent must process them in order after the scan completes. A crash mid-scan with unprocessed buffered events means those events are absorbed by the post-scan `work_queue()` (step 4a) — which is correct per forge-read-pattern. Document this explicitly.

- **Risk 6: DM PR-merge-wait doesn't recheck issue labels during wait** — **Severity: MEDIUM** — `pr-merge-wait.md` specifies DM re-forge-reads the PR on each Monitor wake, but only the PR's merge/conflict state — not the issue's labels. If an operator adds a `pending-human-review` label during the wait, DM won't detect it until the PR reaches a terminal state or the stalled-PR ceiling is hit (which defaults to unbounded). This means an operator redirect could be delayed indefinitely. **Mitigation**: On each Monitor wake during the wait, DM should also re-check the issue's current labels (a cheap `tracker.py get-state <number>` call) and honor operator redirections immediately, not just at End-Of-Task Re-Read.

## Edge Cases

- **Cursor at head (empty poll result)**: `event_poll.py` — when `since` cursor points at the most recent event, `get_since_with_eviction` returns an empty list and no eviction marker. The poll loop sleeps and retries. Correct behavior, no gap.
- **Eviction with role filter stripping all events**: `event_poll.py:204-237` — re-anchors to `oldest_id` first, then the per-event loop runs (possibly empty if role filter strips everything). The cursor advances past the evicted region, and the next poll starts from `oldest_id`. This is the correct forward-progress guarantee documented at line 214-221.
- **Malformed event (no id field)**: `event_poll.py:244-250` — skipped with warning; cursor does NOT advance. Next poll re-fetches it. This prevents silent data loss but could cause an infinite stall if a malformed event is stuck at the head of the deque. The harness should validate event shape at POST time (currently only validates `event_type` and `role` at `harness.py:1478-1481`).
- **Double bootup-complete emission**: `event_bus.py:123-136` — `bootup_complete()` is documented as "Safe to call multiple times." The harness handler (`harness.py:1517-1530`) sets `bootup_complete = True` idempotently under `state._lock`. Correct.
- **Crash mid-scan recovery**: `idle-cooldown-loop.md` — On boot, if working-state shows `Status: running`, the agent restarts the scan from scratch. After completion, runs `work_queue()` (step 4a). Correct — idempotent scan + queue re-check catches tasks that arrived during the outage.
- **Event_id that looks like a cursor (empty string "0")**: `event_poll.py:88` — empty string cursor is passed as `since=""` to `_build_url`. The harness's `get_since_with_eviction` treats empty `since_id` as "no cursor" and returns newest-first. This is correct — an empty cursor defaults to "start from now."

## Integration Risks

- **Harness `/events/{event_id}/complete` endpoint with no consumer**: `harness.py:1688-1743` implements a full closure endpoint (`POST /events/{event_id}/complete`) that executes mechanical side effects (transitions, comments, commits). This is Phase 4 plumbing that no agent currently calls. If an agent started calling it before the `_execute_transition` / `_execute_comment` helpers were fully hardened, status transitions could be executed without the tracker.py authority checks. **Risk**: Low today (no callers), but the endpoint is live and accepting requests. Consider gating it behind a config flag until Phase 4 is complete.
- **`event_poll.py` vs `event_bus_reader.py` divergence**: `event_poll.py` is the Monitor-tool streaming consumer (used by event-mode agents). `event_bus_reader.py` is the mechanical-layer consumer (used by `cycle_pre.py` for polling-mode agents). They query the same `GET /events` endpoint but have different error handling: `event_poll.py` has exponential backoff + retry, while `event_bus_reader.py` has a 500ms timeout + silent-empty fallback. If a polling-mode agent's `cycle_pre.py` receives an eviction signal, `event_bus_reader.py` silently drops it (it doesn't parse the `evicted` key in the response). This means polling-mode agents never detect eviction gaps. **Risk**: Low — polling agents don't maintain a cursor across cycles; each cycle reads recent events without `since`.
- **Config field `event-driven-{role}` resolution duplication**: The wake-mode resolution logic is duplicated across four files: `compose.py:_get_wake_mode` (line 55), `cycle_post.py:_get_role_wake_mode` (line 85), `statusline_data.py:_get_wake_mode` (line 41), and `boot-bootstrap.md` Step 1 (prose-based, not code). If the resolution rules ever change, four places must be updated. **Risk**: MEDIUM for future maintenance drift. **Mitigation**: Extract a shared `get_wake_mode(role)` into `config.py`.

## Open Questions

- **Q1**: Should `event_poll.py` emit an ack after advancing the cursor, so the EventLifecycleManager's in-flight tracking has a consumer? **Why**: Without acks, the `.event-state.json` file grows unboundedly with dispatched-but-never-acked events, and the timeout scanner produces log spam every 10 minutes per event.
- **Q2**: Should `GET /events/for/{role}`'s `dispatch()` call be gated on a config flag or removed until Phase 4 is fully wired? **Why**: The dispatch path persists state and runs a timeout scanner, but no downstream system consumes the in-flight data.
