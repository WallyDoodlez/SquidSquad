## Operator request (2026-06-15)
"Add a task to deal with the status bar to make it work with our event model also. There's a mode change between event and loop."

## Problem
The status bar (per-agent `current-state` display) was originally built around the **LOOP-mode cadence**: each `/loop` cycle updates `current-state` on a fixed interval, and freshness was judged by file age. Under the **EVENT model** the cadence differs — an event-mode agent legitimately does NOT update `current-state` while idle between nudges, and in PM inline/operator sessions the cycle wrappers do not fire at all. So pure file-age freshness misreads a legitimately-idle event-mode agent as stale/stalled.

## What already exists (research, 2026-06-16 — DO NOT rebuild)
`statusline_data.py` already branches on wake mode (#9745 / #9747):
- `_get_wake_mode(role)` → `config.get_wake_mode(role)` is the canonical wake-mode source (resolves original design-Q1).
- `cmd_mode <role>` prints `event-driven` / `polling`.
- `cmd_phase <role>` in **event mode pulls phase + intent from the harness** (not the stale `current-state` file) — so the core "don't read a stale file for an idle event agent" mechanism is already present.

This task is therefore NOT a from-scratch build. It closes the narrow remaining gaps below.

## Design decisions (RESOLVED — operator-approved 2026-06-16)
- **Q1 (where mode is read from):** RESOLVED by existing code — `config.get_wake_mode`. No new source.
- **Q2 / Q3 (event-mode freshness + relationship to #12271 / #12410):** **DECOUPLE.** This task ships the mode-aware display + suppresses false staleness now. Consuming #12271's activity-heartbeat as the positive event-mode liveness signal is an explicit **FAST-FOLLOW**, out of scope here (file post-#12460 cutover). Do NOT couple this task to the cutover landing.
- **Inline / no-wrapper case:** show as a **distinct, clearly-labelled state** (e.g. `inline / operator session`), NOT folded into generic "idle" and NOT shown as stalled/broken.

## Scope (narrowed)
1. Ensure the **wake mode (event / loop) is visibly displayed** in the statusline (confirm the statusline consumes `statusline_data.py mode`; wire it if not).
2. Ensure a **legitimately-idle event-mode agent** is not rendered as stalled (lean on the existing harness-phase path; no file-age "stalled" verdict in event mode).
3. Represent the **inline / no-wrapper** agent as its own labelled state.
4. Preserve **loop-mode** staleness-on-missed-interval behavior (regression guard).
5. Tests for all of the above.

## Acceptance Criteria (refined — testable)
1. The statusline output shows each agent's wake mode (`event` vs `loop`) — verified for both an event-mode and a loop-mode agent.
2. A legitimately-idle EVENT-mode agent (old `current-state` file, no recent nudge) is shown healthy/idle, NOT stalled — deterministic test.
3. A LOOP-mode agent is still flagged stale on a missed interval — regression test (existing behavior preserved).
4. An **inline / no-wrapper** agent (event-mode role, wrappers not firing, no live harness phase) renders as a distinct labelled state (not stalled/broken) — deterministic test.
5. Event-mode rendering applies **no file-age staleness verdict** (no false "stalled"). Consuming #12271 activity-heartbeat is explicitly OUT OF SCOPE (fast-follow).
6. Unit tests cover the mode-aware freshness logic, the inline representation, and the loop-mode regression.
7. `references/installer-files.txt` updated only if a new file is added (in-place edits to existing tracked scripts need no change).
