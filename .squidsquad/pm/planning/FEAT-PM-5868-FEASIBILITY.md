# FEAT-PM-5868-FEASIBILITY Research — Event Consumption Sub-Skill: Compose-Time Reaction Config & Runtime Mechanical Execution

## Summary

This research assesses whether 9 locked design decisions for the Event Reactions feature (#5868) can be implemented in the current SquidSquad codebase without contradiction or hidden blockers. The feature adds an `## Event Reactions` section to `config.md` (both `emits` and `reacts-to` per role), makes `cycle_pre.py` read its per-role event filters and mechanical reactions from config instead of hardcoded constants, adds a cross-agent validation pass to every compose, and adds an `event-reactions.md` sub-skill for creative-phase guidance.

**Primary finding: FEASIBLE WITH CAVEATS.** Three of the 9 locked decisions contain contradictions or under-specification that will produce broken behavior if implemented literally. Two hidden blockers exist in the current codebase. All are resolvable with targeted refinements.

The most consequential caveat: the "hardcoded emission catalog as ground truth" (Decision 2) conflicts with the existing `_ROLE_EVENT_TYPES` filter in `cycle_pre.py` (lines 377-383), which already references three event types (`verification-failed`, `verification-passed`, `agent-health`) that **no script in the codebase emits**. If the locked decision's validation rule ("extra emits = error") is applied literally, those three filter entries become errors — but they've been the production behavior since #5622 shipped. The emission catalog also doesn't account for events the system intends to emit but hasn't yet (`phase-change` — handled by harness at harness.py:751,799 but never emitted by any script).

## Side Effects

- **Risk 1: `verification-failed`/`verification-passed`/`agent-health` are phantom event types — ground-truth catalog would reject them as errors** — The current `_ROLE_EVENT_TYPES` filter (cycle_pre.py lines 377-383) references 7 event types, but only 10 are actually emitted by scripts. Three filter entries (`verification-failed`, `verification-passed`, `agent-health`) have no corresponding emission site. If the locked decision applies literally (extra emits = error), the derivation would flag these as invalid — yet cycle_pre.py has been filtering for them since #5622 shipped. Similarly, `phase-change` is handled by harness.py (lines 751, 799) but never emitted. — Severity: **H** — Mitigation: The emission catalog must distinguish "emitted by scripts" (hard constraint) from "expected by the system" (soft constraint). `verification-*` and `agent-health` are expected events that agents will emit from creative phase or that are planned but not yet implemented. The ground-truth catalog should include them as "allowed" even if not yet emitted, or the validation rule needs a third category: "referenced by filter/consumer but not emitted = warning, not error."

- **Risk 2: Every compose runs LLM derivation — breaks CI/offline/upgrade paths** — Currently `agent_compose()` (line 550) is gated behind `agent-compose: yes` (line 87 — currently `no`). The locked decision requires LLM derivation on EVERY compose. This would call Claude CLI from every `compose.py deploy` invocation, including CI test runs, offline development, and automated upgrades. The deterministic compose path (tests, CI) would fail or hang on missing Claude CLI. — Severity: **H** — Mitigation: Add a `--no-llm` flag or TTY detection (non-interactive = skip derivation, validate only). The locked decision must accommodate: "derivation runs every compose **when LLM is available**; in non-interactive/CI mode, validate-only against existing contract (or hardcoded defaults)."

- **Risk 3: Cross-agent validation after single-role deploys has incomplete data** — If only skill is deployed (`compose.py deploy skill`), the validation must check skill's contract against pm/qa/dm — but those agents' CLAUDE.md files may be stale or from a prior compose. Single-role deploys produce partial contract views. — Severity: **M** — Mitigation: Validation should check against the config.md Event Reactions section (canonical source) not against each agent's CLAUDE.md. The config.md section is the cross-agent contract registry.

- **Risk 4: LLM derivation prompt engineering complexity** — The locked decision says "Agent detects instruction changes and re-populates." This requires the LLM to diff L1-L4 sources against the existing config.md section, detect meaningful changes, and selectively update. Current `agent_compose()` (line 550) does NOT do this — it unconditionally rewrites the entire output. Change detection doubles the derivation prompt size and increases hallucination risk. — Severity: **M** — Mitigation: Phase 1: always regenerate (simpler, safe when gated). Phase 2: add change detection. The "detect changes" requirement should be deferred.

## Edge Cases

- **Event Reactions section absent (graceful degradation)**: `cycle_pre.py` falls back to hardcoded `_ROLE_EVENT_TYPES` (line 377) and `_run_mechanical_reactions()` (line 398). This is already correct — the fallback path exists and produces identical behavior to today. No change needed.

- **No harness running (events unreachable)**: `event_bus_reader.query()` returns `[]` (line 89 of event_bus_reader.py). `mechanical_reactions` is empty. Agent sees empty `recent_events`. Graceful degradation already in place.

- **Role added to config but not yet deployed**: Cross-agent validation should only verify contracts for roles that exist on disk (CLAUDE.md present). Checking contracts for non-existent agents would produce spurious validation failures.

- **L4 project sub-skills define custom event behavior**: L4 content in `.squidsquad/project/` can introduce event relationships the hardcoded catalog doesn't cover. Locked decision says "hallucinated events = error" — but L4 events are legitimate extensions. The tiered authority model (catalog events = hard constraint; L4 events = allowed with warning) is needed but not specified in the locked decisions.

- **Event loop / cascade**: Mechanical reactions that trigger tracker transitions emit new `status-transition` events (tracker.py line 990). If a reaction to `pr-merge` triggers a transition, the transition emits a new event which could re-trigger reactions. The current code mitigates this with self-event filtering (cycle_pre.py line 413: `if event.get("role") == role: continue`) and cursor-based deduplication (same event ID won't be read twice). Config-driven reactions must preserve these safeguards.

## Open Questions

- **Q1**: Should `verification-failed`, `verification-passed`, and `agent-health` be in the ground-truth emission catalog even though no script currently emits them? — **Why**: They appear in the production `_ROLE_EVENT_TYPES` filter (cycle_pre.py lines 378-382), so agents already listen for them. If the catalog excludes them, the LLM derivation correctly listing them becomes an "error." If the catalog includes them, there's no emission site to validate against. The locked decision's binary "missing = warning, extra = error" framing doesn't handle "expected but not yet emitted." **Recommendation**: Add a third catalog category — "system-recognized" — for event types referenced by filters or harness but not yet emitted by scripts. Treat them as "allowed but unvalidated" (warn, don't error).

- **Q2**: How does "every compose runs LLM derivation" interact with CI and offline development? — **Why**: CI runs `compose.py` without Claude CLI. Offline developers compose without API access. The locked decision says "LLM derivation runs automatically on EVERY compose" but the current architecture gates LLM behind `agent-compose: yes` (which is `no`). If the derivation is mandatory, CI breaks. If it's optional, the locked decision is violated. **Recommendation**: Derivation is always attempted but gracefully skipped when Claude CLI is unavailable. Non-interactive mode (CI, upgrade) skips derivation and validates against existing contracts (or passes vacuously if absent). This respects both the locked decision's intent and operational reality.

- **Q3**: How can validation present "process-gap language" without knowing internal event vocabulary? — **Why**: The locked decision says failures are presented in "plain process-gap language (not event names)." This requires translating event type strings (`pr-merge`, `status-transition`) into human-readable descriptions ("pull request was merged", "issue status changed"). The system must maintain a mapping table. If event types are derived from LLM or L4 sources, their human-readable descriptions must also be derived or defaulted. **Recommendation**: The hardcoded emission catalog includes a `description` field for each event type. For L4/unknown events, use a generic format: `"<role> expects to react to an event that no agent emits"`. Validation output renders the gap in process terms, not raw event names. This is implementable but adds a small translation layer.

- **Q4**: What is the estimated token cost per compose for the derivation step? — **Why**: The locked decision says "Token cost accepted" but the team should know what they're accepting. **Estimate**: The current `agent_compose()` prompt (compose.py lines 573-588) sends the full composed CLAUDE.md (~5-15K tokens per role) plus fixed instructions (~1K). Event contract derivation would need a different prompt — scanning L1-L4 sources for event-related patterns. If done naively (send all 4 roles' full composed output), that's ~40-80K input tokens + ~5-10K output tokens = ~50-90K total per compose-all. At Claude API prices (~$3/1M input, $15/1M output), roughly $0.25-$0.75 per compose-all. A focused derivation prompt (scan only sub-skills that reference events, not full CLAUDE.md) could reduce this to ~$0.10-$0.30. At 48 composes/day (every 30 minutes), worst-case daily cost: ~$12-$36/day. This is material but not prohibitive.

- **Q5**: Does the "agent detects instruction changes" requirement need change detection, or can it simply regenerate every time? — **Why**: The locked decision says "Agent detects instruction changes and re-populates." Change detection requires diffing L1-L4 sources against the existing config.md section, which doubles the prompt size and complexity. If the derivation simply regenerates every time (no change detection), it's simpler but burns tokens unnecessarily on no-change composes. The locked decision may be over-specified for Phase 1. **Recommendation**: Phase 1: regenerate on every compose (simple, correct). Phase 2: add change detection to skip regeneration when nothing changed. The locked decision's "detects changes" language should be treated as aspirational, not blocking.

## Recommendation

**FEASIBLE WITH CAVEATS.** The implementation is 80% straightforward mechanical work that maps cleanly onto the existing architecture. The remaining 20% consists of three resolvable contradictions in the locked decisions and two hidden blockers:

**Contradictions requiring resolution before implementation:**
1. **Decision 2 (emission catalog as ground truth)** contradicts the existing `_ROLE_EVENT_TYPES` filter which references 3 event types no script emits. Resolution: catalog needs a third "recognized but not emitted" category.
2. **Decision 3 (LLM derivation every compose)** contradicts the current `agent-compose: no` default and breaks CI. Resolution: derivation is always-attempted but gracefully skipped when Claude CLI unavailable.
3. **Decision 4 (process-gap language without event names)** requires a translation layer not specified in the locked decisions. Resolution: emission catalog includes per-type human-readable descriptions.

**Hidden blockers:**
- `phase-change` is handled by harness.py but never emitted — it should be in the catalog if the system recognizes it.
- The `_run_mechanical_reactions()` function (cycle_pre.py line 398) currently hardcodes reaction logic for `pr-merge` and `verification-failed`. Converting these to config-driven dispatch while preserving backward compatibility requires careful dual-mode design (config reactions as additive overrides to compiled-in defaults).

**Recommended implementation order:**
1. First: emission catalog + config.md section + config.py field mappings (no LLM, no validation)
2. Second: cycle_pre.py refactoring to read from config.md (hardcoded fallback preserved)
3. Third: cross-agent validation (deterministic, no LLM) — validates catalog against emission sites + config.md consistency
4. Fourth: event-reactions.md sub-skill
5. Fifth: LLM derivation (gated behind Claude availability, with graceful skip)

## Vault Candidates

- **Type**: learning — "Emission catalog must distinguish emitted-from-scripts vs recognized-by-system vs phantom" — **Why**: The current `_ROLE_EVENT_TYPES` filter references events no script emits. Any ground-truth catalog that doesn't account for "expected but not yet implemented" event types will produce false-positive validation errors. This applies to any future event-driven system where the consumer filter predates the producer implementation.

- **Type**: pattern — "Config-driven dispatch with compiled-in fallback for mechanical reactions" — **Why**: `cycle_pre.py`'s `_run_mechanical_reactions()` currently uses hardcoded if/else. The refactoring to config-driven dispatch (+ hardcoded defaults as fallback) is a reusable pattern for any mechanical script that needs to become configurable without breaking existing behavior on upgrade.

- **Type**: decision — "Event Reactions config section covers both emits and reacts-to per role" — **Why**: Already flagged in PM research. This is a permanent schema decision for config.md. All future event types must follow this compact per-role format. Worth vaulting because it constrains the config.md schema permanently.

- **Type**: pattern — "Two-tier validation: hard catalog constraints + L4 allowance with warning" — **Why**: The validation model where known emission types are hard constraints (errors) but L4/unknown types are allowed with warnings is a general pattern for any system that validates LLM-derived structured data against code-extracted ground truth. Applicable beyond event contracts.
