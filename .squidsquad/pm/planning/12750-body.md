## Operator directive (2026-06-17)
Today PM commits each task's planning doc **directly to `main`** (442 plan files already live in `.squidsquad/*/planning/` on main). Decouple that: **push the plan into the task PR, not main.** Committing the plan onto a fresh task branch **spawns the draft PR**; the worker implements on that same branch; on merge the plan lands in `main` **co-located with the code that fulfilled it** — one permanent, reviewable track record.

Capture as an **L2 instruction** (generic delivery behavior, not project-specific).

## Current process (to replace)
- PM authors plan → `.squidsquad/<role>/planning/<n>-body.md`, pushes it to the GitHub issue body **and commits the file straight to `main`**.
- The worker later opens a separate task branch + PR for the code only.
- Result: plan on main, code in the PR — decoupled; the PR never carries the plan that justified it.

## New process (target)
1. **PM, at end of planning:** create branch `squidsquad/task/<n>` from main, commit the plan file as the **first commit** (`plan(#<n>): <title>`), push → **open a DRAFT PR** seeded with just the plan. **Do NOT commit the plan to main directly.**
2. **Worker, on pickup:** check out the **existing** plan-seeded branch (do NOT create a new one); the plan is already commit 1; add implementation commits on top; flip the PR to ready when done.
3. **On merge:** the plan file merges into `main` alongside the implementation → permanent co-located track record.
4. **Issue body:** stays the bus — short summary + link to the draft PR. The **committed plan file in the PR is the source of truth** for the spec (issue body is the synced copy). Strengthens [[feedback_issue_body_must_match_context]]: one authoring location.

## Scope (L2 instruction + descriptive sync — one delivery)
- **L2 `references/roles/pm/`** — planning-completion step: commit plan to a new task branch + open draft PR; never commit the plan to main directly.
- **L2 `references/roles/worker/`** — branch step: adopt the existing plan-seeded branch instead of creating a fresh one; implementation rides on top of the plan commit.
- **Descriptive sync (same delivery):** `docs/AGENT-RUNTIME.md` task-lifecycle (+ `docs/ARCHITECTURE.md` if it describes plan→main) → reflect plan-into-PR.
- Plan files stay tracked and merge into the repo (track record) — confirm they remain **project-local** (not added to `installer-files.txt`; not shipped to target repos).

## Acceptance criteria
1. Composed PM instructions: end-of-planning → branch `squidsquad/task/<n>` + commit plan (`plan(#<n>)`) + open **draft** PR; plan is **not** committed to main directly.
2. Composed worker instructions: adopt the existing plan-seeded branch; do not recreate; implementation commits ride on top of the plan commit.
3. On PR merge, the plan file is present in `main` co-located with the implementation (verify on a sample merge).
4. Descriptive lifecycle docs (AGENT-RUNTIME; ARCHITECTURE if applicable) match — zero stale "PM commits the plan to main" descriptions remain (grep clean).
5. Plan files remain project-local — not in `installer-files.txt`, not shipped to target repos.
6. `compose.py deploy-all` green.
7. **Comprehension test:** a fresh PM agent quizzed *"after you finish planning a task, where does the plan go?"* answers "committed onto a new `squidsquad/task/<n>` branch as the first commit, which opens a draft PR — never straight to main"; a fresh worker quizzed *"do you create the task branch?"* answers "no — I adopt the existing plan-seeded branch."
