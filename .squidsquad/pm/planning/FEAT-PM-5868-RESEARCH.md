# FEAT-PM-5868 Research — Event consumption sub-skill: compose-time reaction config, runtime mechanical execution

## Summary

This research covers adding an **Event Reactions** section to `config.md` that defines what events each agent role **emits** and **reacts-to**, making event contracts explicit and compose-time-validated. The change builds on the shipped #5888 (compose skill — `compose.py` with L1-L4 assembly) and #5856/#5622 (event bus emission/consumption — `event_bus.py`, `event_bus_reader.py`, and `cycle_pre.py` mechanical reactions).

Currently, event emissions are hardcoded across four scripts (`tracker.py`, `git_ops.py`, `cycle_pre.py`, `cycle_post.py`) with 10 event types. Per-role relevance filtering and mechanical reactions are hardcoded in `cycle_pre.py` (lines 377-439). There is no sub-skill that documents event consumption behavior for the creative phase — the `cycle-runner` sub-skill only mentions `recent_events` and `mechanical_reactions` as informational fields. The `agent_compose()` LLM step in `compose.py` (line 550) currently only polishes prose coherence; extending it to derive event contracts from L1-L4 source text is feasible but carries risk of hallucination.

**Recommendation**: Feasible with caveats. The config.md extension and cross-agent validation are straightforward mechanical work. The creative LLM derivation of event contracts is the high-risk component — it depends on Claude correctly parsing multi-layer markdown instructions and inferring implicit event contracts. The interactive fix loop adds complexity that should be scoped carefully to avoid blocking composes indefinitely.

## Side Effects

- **Risk 1: LLM-derived event contracts hallucinate emits/reacts** — The creative LLM step (`agent_compose()`) must read L1-L4 source text and infer what events each role emits and reacts to. L1-L4 instructions are prose-heavy and don't use structured event descriptions. The LLM may invent event types that don't exist or miss real ones. — **Severity: H** — **Mitigation**: (a) The LLM derivation only writes to config.md when `agent-compose: yes` (currently disabled). (b) Deterministic cross-agent validation catches missing/invalid contracts — if validation fails, the compose aborts or enters fix loop. (c) Hardcoded base event type catalog in compose.py acts as ground truth for validation (all known event types from emission sites). (d) The config.md `Event Reactions` section can be manually authored or corrected without the LLM step.

- **Risk 2: config.md bloat from event reaction config** — Adding per-role `emits` and `reacts-to` entries for 4 roles × ~10 event types creates 40-80 config lines. This could push config.md past the point where agents can efficiently parse it. — **Severity: M** — **Mitigation**: (a) Compact format — single `- **<role> emits**: event1, event2` + `- **<role> reacts-to**: event3, event4` per role (8 lines total). (b) Config.md is only read by mechanical scripts, not parsed by LLM agents inline (agents use `config.py get`).

- **Risk 3: Mechanical reaction refactoring introduces regression** — `_run_mechanical_reactions()` currently works with hardcoded if/else. Refactoring to config-driven dispatch could introduce subtle behavioral changes (ordering, error handling, missed edge cases). — **Severity: H** — **Mitigation**: (a) Keep hardcoded reactions as compiled-in defaults; config.md reactions are additive overrides, not replacements. (b) Default to current hardcoded behavior when config section is absent (graceful degradation). (c) `test_event_bus_reader.py` and `test_cycle_pre.py` must pass without modification when config section is absent.

- **Risk 4: Interactive fix loop blocks agent deployment** — If validation fails and the fix loop requires human input, automated deploy workflows (CI, upgrade, setup) can deadlock. — **Severity: M** — **Mitigation**: (a) Non-interactive mode (detected via `--yes` flag or missing TTY) skips fix loop, logs warnings, deploys with whatever contracts exist. (b) Fix loop timeout: 2 minutes max, then fall through with warnings.

## Open Questions

- **Q1**: Should the LLM derivation of event contracts run on every compose or only when `agent-compose: yes`? — **Why**: If it runs on every compose, the deterministic CI path (which skips Claude calls) would never derive contracts. If it only runs with `agent-compose: yes`, config.md stays stale unless a human enables it. The task says "compose.py creative LLM step derives event contract from L1-L4 instructions" — this implies it's part of the `agent_compose()` step, which only runs when `agent-compose: yes`. But the config.md section needs to be populated somehow on first deploy. **Recommendation**: First-time population happens during setup (`/squidsquad-setup` → scaffold → compose with agent-compose enabled). Subsequent composes without `agent-compose: yes` validate existing contracts but don't regenerate them.

- **Q2**: What is the authoritative source when LLM-derived contracts conflict with hardcoded emission sites? — **Why**: If `agent_compose()` determines PM emits `foo` but `tracker.py` doesn't emit `foo`, the validation should flag the LLM as wrong (emission sites are ground truth per the task: "existing mechanical emissions stay hardcoded in scripts"). But if `agent_compose()` misses a real emission (`git_ops.py` emits `pr-create` but LLM doesn't list it), the contract is incomplete. **Recommendation**: Validation compares derived contracts against a hardcoded ground-truth catalog extracted from emission site code. Missing emits → warning. Extra emits → error. This aligns with the human's "prefers direct/mechanical checks" preference.

- **Q3**: Should the interactive fix loop pause for human input or allow agent self-correction? — **Why**: If the fix loop requires human input and the human is offline, compose blocks indefinitely. If it allows agent self-correction, the agent might patch config.md incorrectly. The self-healing sentinel pattern (two-tier) suggests agents should try Tier 1 (self-correct obvious gaps) before escalating to Tier 2 (human). **Recommendation**: Tier 1 — agent can auto-fill missing `emits` entries from hardcoded catalog (deterministic). Tier 2 — agent proposes reactions and asks human to confirm. Timeout after 2 minutes falls through with logged warnings.

- **Q4**: Should the `Event Reactions` section cover creative-phase reactions or only mechanical reactions? — **Why**: `cycle-runner.md` already tells agents to examine `recent_events` and `mechanical_reactions` in `cycle-input.json` and "investigate anomalies." A dedicated `event-reactions` sub-skill would add structured guidance for what each event type means for creative-phase work. But the config.md section is mainly consumed by `cycle_pre.py` (mechanical layer). **Recommendation**: Config.md covers mechanical reactions (consumed by `cycle_pre.py`). The `event-reactions.md` sub-skill covers creative-phase guidance (consumed by agents during Ralph Loop). Both are needed; they serve different layers.

## Recommendation

**Feasible with caveats.** The mechanical infrastructure changes (config.md section, config.py field mappings, cycle_pre.py refactoring, validation script, event-reactions sub-skill) are straightforward and well-understood. The creative LLM derivation step is the high-risk component — it requires Claude to accurately parse L1-L4 markdown instructions and infer event contracts without hallucination. Three guardrails make this acceptable: (1) hardcoded ground-truth catalog for validation, (2) `agent-compose: yes` gating (currently disabled, giving time to refine), (3) deterministic fallback when LLM output fails validation. The interactive fix loop should be scoped conservatively — Tier 1 auto-fixes from ground truth, Tier 2 prompts human, timeout prevents deadlock.
