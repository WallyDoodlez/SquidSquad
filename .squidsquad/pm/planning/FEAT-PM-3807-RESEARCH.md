# FEAT-PM-3807 Research: Universal Sentinel-Based Agent Lifecycle

**Task**: #3807 — Rewrite agent lifecycle management
**Date**: 2026-04-27
**Status**: Research complete

---

## Summary

The current agent lifecycle is fragmented across 5 script entry points, 2 sentinel types, and per-agent boot logic baked into templates. There are two categories of restart: the wrapper's `.restart` sentinel (already works) and the PM's `boot_remote.py` auto-boot (runs every cycle pre). The proposed architecture unifies all triggers through a single `.stop-after-cycle` sentinel that the wrapper writes, the agent reads at cycle end, and the wrapper respawns from — making agents fully passive. The key structural changes are: (1) one `start_team.py` entry point replaces `start-squad.ps1`, `start-squad.sh`, and `boot_remote.py --all`, (2) the `.stop-after-cycle` sentinel replaces agents writing `.restart` themselves, (3) context-pressure-triggered respawn moves entirely to the wrapper, (4) PM stops auto-booting agents and instead reports missing agents to the human.

## Current Architecture — Detailed Inventory

### Entry Points (How Agents Get Started)

**1. `references/scripts/boot_remote.py`**
- Reads `.squidsquad/.local-config` for clone paths per role
- Reads `config.md` for Dev Agents list and DM/QA presence
- Checks agent liveness: `.health` heartbeat (primary), `.pid` file (fallback)
- If dead and no `.stop` sentinel: finds `start-{role}.ps1` or `.sh`, spawns in a new terminal
- Uses `.booting` sentinel to prevent double-spawns (TTL 30s, atomic write)
- Cleans stale `.restart` sentinels before spawning a dead agent
- Used by: `cycle_pre.py` (PM's `_build_pm_input`), `start-squad.ps1/.sh`, `reboot_agent.py` (spawning logic)

**2. `references/scripts/reboot_agent.py`**
- Imports `boot_remote` for clone-path resolution and terminal spawning
- If wrapper (`.pid`) is dead: calls `_spawn_wrapper` → `boot_remote._spawn_terminal`
- If wrapper alive but claude dead: writes `.restart` sentinel, waits
- If both alive: writes `.restart` sentinel, then waits for `current-state` to show `idle`, kills `.claude-pid` process, wrapper respawns on next check
- `--force` flag: skips idle wait, kills immediately
- `--all` flag: iterates all agents including PM
- Used by: agent templates (`agent-lifecycle.md`), human, automated tasks

**3. `.squidsquad/start-{role}.ps1` / `start-{role}.sh`**
- Generated by `compose.py boot {role}` from `references/templates/start-role.{ps1|sh}`
- One file per role, role-specific (hardcoded `SQUIDSQUAD_ROLE={{ROLE}}`)
- Does: PID singleton lock, pre-flight (gh auth, working branch checkout, git pull), heartbeat background job, spawn claude, check `.restart` sentinel on exit, one crash retry on non-zero exit
- Contains wrapper logic inline — **not a thin launcher**

**4. `.squidsquad/start-squad.ps1` / `start-squad.sh`**
- Trivially calls `python references/scripts/boot_remote.py --all`
- No wrapper logic — purely delegates

**5. `references/scripts/add_role.py --boot`**
- Optional boot after cloning a new agent role
- Delegates to the role's `start-{role}.ps1/.sh` — does not call `boot_remote`

### Wrapper Logic (Per-Role Boot Scripts)

Each `start-{role}.ps1/.sh` (generated from `start-role.{ps1|sh}`) contains:

**Sentinel files written by wrapper:**
- `.pid` — wrapper process PID (singleton lock, removed on exit)
- `.health` — heartbeat epoch every 5s (background job/subshell; set to `dead` on exit)
- `.claude-pid` — claude subprocess PID (written after spawn; removed on exit)
- `current-state` — phase|description status (written throughout lifecycle)

**Sentinel files read by wrapper:**
- `.restart` — if present after claude exits, wrapper removes it and respawns once

**Restart logic in current wrapper:**
1. Spawn claude subprocess
2. Wait for exit
3. If `.restart` exists → remove it, sleep 2s, respawn claude (one time only)
4. If non-zero exit code → one crash retry (sleep 2s, respawn)
5. Wrapper exits after these attempts

**Critical gap**: The wrapper only respawns once for `.restart`. If the agent writes `.restart` again in the second run, it is NOT honoured — the wrapper has already used its single-respawn slot.

### Clone Isolation and Boot Scripts

`add_role.py` flow:
1. `git clone --local` to create per-role clone
2. Fix origin remote to upstream URL
3. `compose.py deploy {role}` → writes `CLAUDE.md` + `SOUL.md` to clone's `.squidsquad/{role}/`
4. `compose.py boot {role}` → generates `start-{role}.ps1/.sh` in clone's `.squidsquad/`
5. `_sync_local_config` → writes `.squidsquad/.local-config` to all known clones

Each clone runs its own wrapper script (`start-{role}.ps1`), which is specific to that role. The wrapper lives *inside the clone* at the clone's `.squidsquad/` path.

**Key constraint for `start_team.py`**: Since each agent lives in a separate clone at a different filesystem path, a single entry point must read `.local-config` to find each clone path, then spawn each agent's boot script in its clone directory. It cannot run all agents from one directory.

## Proposed Architecture — Sentinel-Based Unified Flow

### Core Design Principle

The wrapper owns ALL restart decisions. Agents are passive — they observe a sentinel at cycle end and exit cleanly. The wrapper observes the exit, decides what to do next (respawn, wait for human, back off), and acts.

### New Sentinel: `.stop-after-cycle`

- Written by: wrapper (context pressure threshold exceeded), `start_team.py` (human reboot), any external script
- Read by: `cycle_post.py` (at cycle end, before writing `.restart`)
- Behaviour on detection: agent finishes current cycle normally, `cycle_post.py` exits with a special code or writes a clean-exit marker, wrapper sees clean exit + sentinel → respawns fresh

### Proposed `start_team.py` Entry Point

Replaces: `start-squad.ps1`, `start-squad.sh`, `boot_remote.py --all` as primary entry point

Responsibilities:
- Parse `.local-config` for role→clone path mapping
- For each role: check liveness, spawn in appropriate terminal/session if dead
- Accept `--role <name>` for single-role boot
- Accept `--reboot <role>` for sentinel-based restart (writes `.stop-after-cycle`, waits for clean exit, then re-launches)
- Accept `--stop <role>` to write `.stop` sentinel
- Accept `--all` (default) for all agents

### Wrapper Changes (to `start-role.ps1` / `start-role.sh` template)

Current wrapper restart logic (single `.restart` check after claude exit) replaced with:

```
loop:
  spawn claude
  wait for exit

  if .stop-after-cycle exists:
    remove .stop-after-cycle
    if .stop exists:
      exit wrapper (agent explicitly stopped)
    else:
      log "clean cycle exit, respawning..."
      sleep 2
      continue loop

  if exit_code != 0:
    one crash retry, then exit wrapper
  else:
    exit wrapper (agent decided to stop — respawn not requested)
```

Context pressure detection moves to wrapper:
- Wrapper reads `context-pressure` file after each claude exit
- If pressure > threshold: write `.stop-after-cycle`, respawn
- Agent no longer sets `restart_needed` for context pressure — just exits cleanly

### PM Role Changes

- Remove: auto-boot call in `cycle_pre.py` (`boot_remote.py --all --dry-run`)
- Remove: `boot-remote-agents` sub-skill from PM template
- Add: PM health check on cycle 1 only — reads `health_check.py` output, reports any missing agents to human via check-in message, does NOT boot them
- PM never calls `reboot_agent.py` or `boot_remote.py` autonomously

### Agent Template Changes

- Remove `self-restart.md` sub-skill from all templates
- Remove `restart_needed` / `restart_reason` fields from `cycle-output.json` schema
- Remove `_do_restart_sentinel` from `cycle_post.py`
- Add `.stop-after-cycle` check to `cycle_post.py` (read sentinel, exit cleanly if present)

### Behavior Changes

1. **Agents no longer self-restart**: Agents that previously set `restart_needed: true` for context pressure now just finish their cycle and exit. The wrapper detects the clean exit + `context-pressure` file and writes `.stop-after-cycle` before the next spawn.

2. **Wrapper loops indefinitely**: The wrapper no longer exits after the first restart. It stays alive and respawns as long as `.stop` is absent. The only way to stop an agent permanently is to create `.stop`.

3. **PM cycle_pre changes**: The `cycle-input.json` for PM will no longer contain `boot_results`. Any PM template logic referencing `boot_results` must be updated.

4. **Context pressure check timing**: Currently, the agent reads `context-pressure` at the start of its cycle and decides to set `restart_needed`. Under the new model, the wrapper reads `context-pressure` after the agent exits — meaning the threshold check happens post-cycle rather than pre-cycle. The agent may run one more full cycle before the wrapper detects and acts.

5. **Reboot interface changes**: `reboot_agent.py` becomes a thin wrapper or is absorbed into `start_team.py`. The `agent-lifecycle.md` sub-skill documentation changes.

## Side Effects

### HIGH severity

**1. Wrapper loop without a brake can spin on persistent crashes**
- **Risk**: If claude crashes immediately every time (corrupt session, auth failure), the wrapper loops infinitely, consuming resources and creating log noise.
- **Mitigation**: Add exponential backoff on crash: 2s, 4s, 8s, ... up to 5 minutes. Write `.health=backoff` during backoff. After N consecutive crashes (e.g. 5), write `.stop` and exit with `health=error`. Human must intervene.

**2. `.stop-after-cycle` written mid-cycle creates incorrect exit**
- **Risk**: If `start_team.py --reboot` writes `.stop-after-cycle` while the agent is mid-cycle (not at `cycle_post` yet), the agent will see the sentinel at the end of the *current* cycle and exit. This is the intended behavior — but if the cycle takes longer than expected (e.g. 20 minutes of implementation work), the human may be surprised.
- **Mitigation**: Document that `--reboot` is "next-cycle reboot" not "immediate". For immediate reboot, keep `--force` option that kills `.claude-pid` directly.

**3. PM's missing `boot_results` field breaks existing PM CLAUDE.md**
- **Risk**: Deployed PM agents already contain the compiled `boot-remote-agents` sub-skill in their `CLAUDE.md`. Removing it from templates does not update running agents — they still try to process `boot_results` from `cycle-input.json`. After `cycle_pre.py` stops providing `boot_results`, the PM agent gets `null`/missing field and may behave unexpectedly.
- **Mitigation**: Stage the change: (a) have `cycle_pre.py` continue providing `boot_results` (as empty list `[]`) until all agents are redeployed, (b) redeploy all CLAUDE.md files in one pass, (c) remove `boot_results` from `cycle_pre.py` in a follow-up.

**MEDIUM severity**

**4. `.restart` sentinel becomes orphaned**
- **Risk**: Any stale `.restart` files left from the old system will be processed by the new wrapper loop as `.stop-after-cycle` equivalent — or ignored if the wrapper no longer checks `.restart`. If the wrapper now only checks `.stop-after-cycle`, existing `.restart` files are silently ignored, and agents that expected respawn won't get it.
- **Mitigation**: During migration, clean all `.restart` files across all clones before deploying new wrappers. Add a migration step to `start_team.py` startup.

**5. Wrapper context pressure detection has different timing semantics**
- **Risk**: The agent currently checkpoints working-state before signaling restart. Under the new model, if the wrapper triggers restart based on `context-pressure` file, the agent may not have checkpointed. If claude's context is at 90% and the agent is mid-cycle, the wrapper will respawn, but the agent never got a chance to write a proper working-state checkpoint.
- **Mitigation**: The agent template's context pressure step (Step 1b) still runs — it still checkpoints working state. The only change is the agent doesn't also set `restart_needed`. The checkpoint still happens. This risk is LOW upon closer analysis.

**LOW severity**

**6. Terminal proliferation removed**
- Currently `boot_remote.py` spawns each agent in a **new terminal window**. `start_team.py` should preserve this (one terminal per agent). If it instead runs all agents in the same terminal or as background processes, visibility is lost.
- **Mitigation**: `start_team.py` uses the same `_spawn_terminal` logic from `boot_remote.py` (or imports it directly). Each agent still gets its own terminal window.

**7. `reboot_agent.py` users will need to update**
- Any documentation, scripts, or human muscle memory using `python references/scripts/reboot_agent.py skill` needs to migrate to `python references/scripts/start_team.py --reboot skill`.
- **Mitigation**: Keep `reboot_agent.py` as a thin shim that calls `start_team.py --reboot` with a deprecation warning. Remove after one version.

## Edge Cases

### 1. Agent crashes mid-cycle (before cycle_post runs)

**Current behavior**: `cycle_post.py` never runs. No `.restart` is written. Wrapper sees non-zero exit code → one crash retry.

**New behavior**: Same. `.stop-after-cycle` is only relevant at `cycle_post.py` time. Wrapper's crash retry logic handles the mid-cycle crash. The `context-pressure` check in the wrapper also runs after this crash retry.

**Gap**: If the crash happens consistently, the wrapper reaches its crash limit and writes `.stop`. Human sees `.health=dead`. No auto-recovery. This is correct — repeated crashes need human investigation.

### 2. Wrapper crashes or is killed (SIGKILL, power loss)

**Current behavior**: `.health` stops updating. `boot_remote.py` detects stale heartbeat (>15s) and reports `needs_boot`. PM's next cycle sees this and boots the agent.

**New behavior**: Same for health detection. But PM no longer auto-boots — it only reports to human on first cycle. The human must boot manually (via `start_team.py --role <name>`) or the wrapper restarts itself if the terminal session recovers.

**Gap**: Under the old model, the PM would auto-boot a crashed wrapper within one cycle. Under the new model, a crashed wrapper stays down until a human intervenes. This is an intentional degradation of automation — but it changes the SLA for agent recovery.

**Mitigation options**:
- Option A: Accept this — agents that crash badly need human attention anyway
- Option B: Keep a narrow auto-boot for dead wrappers (not for context pressure): PM still calls `start_team.py --role <name>` if `.health` shows dead for >2 cycles. This preserves the "boot dead agents" behavior while removing the "proactive restart" behavior.

### 3. Sentinel written during active cycle (concurrent write)

**Scenario**: `start_team.py --reboot skill` writes `.stop-after-cycle` while skill is in the middle of implementing a feature.

**Behavior**: Agent reaches `cycle_post.py` at end of current cycle. `cycle_post.py` checks `.stop-after-cycle`. Commits pending work. Exits cleanly. Wrapper reads sentinel, respawns.

**Risk**: If the implementation was mid-way through a task (working-state.md has `in-progress`), the respawned agent will resume from working-state correctly. The `cycle_pre.py` `resume-working-state` logic handles this.

**No gap identified** — this case is handled correctly.

### 4. Multiple `.stop-after-cycle` sentinels / concurrent restarts

**Scenario**: Two sources write `.stop-after-cycle` simultaneously (e.g., both `start_team.py --reboot` and context pressure trigger at the same time).

**Behavior**: The file is idempotent — second write overwrites first with the same semantic meaning. `cycle_post.py` reads it once, removes it, exits. Wrapper spawns once.

**No gap identified**.

### 5. Windows-specific issues

**Current `.restart` sentinel and Windows file locking**:
- The current wrapper uses `Remove-Item` before re-reading `.restart` — no issue
- The new wrapper needs to read `context-pressure` after claude exits — this file is written by the statusline hook (a VS Code extension task). If VS Code is closed, the file may be stale.

**Mitigation**: Wrapper checks age of `context-pressure` file. If older than one iteration interval, treat as `0%` (unknown/safe). Do not trigger restart on stale pressure data.

**PowerShell background job for heartbeat**:
- The current `Start-Job` approach for heartbeat works but creates orphaned jobs on crash
- The `finally {}` block cleans up `$heartbeatJob` — this is correct
- No change needed; the new wrapper loop keeps this pattern

**Atomic sentinel writes on Windows**:
- Windows does not support `rename()` atomicity the same way as POSIX
- The existing `[System.IO.File]::WriteAllText` + `Move-Item -Force` pattern is already in place for `.health` — use the same pattern for `.stop-after-cycle`

### 6. Agent template change → reboot needed (DM scenario)

**Current behavior**: DM ships a template change (new CLAUDE.md), then calls `reboot_agent.py <role>` for each affected agent. DM writes `.restart` indirectly or kills the claude process.

**New behavior**: DM calls `start_team.py --reboot <role>`. This writes `.stop-after-cycle` for the agent. Agent finishes current cycle, exits cleanly, wrapper respawns with new CLAUDE.md.

**No gap identified** — behavior is equivalent, interface changes.

### 7. PM is itself restarted while reporting to human

**Scenario**: `start_team.py --reboot pm` is called while PM is in the middle of the human check-in step.

**New behavior**: `.stop-after-cycle` is written. PM finishes its cycle (including the check-in). `cycle_post.py` detects sentinel, exits. Wrapper respawns PM.

**Acceptable** — check-in will complete before restart.

## Integration Risks

### State Branch Integration

The state branch (`squid-squad`) is written to by `cycle_post.py` via `git_ops.py commit-state`. The `.stop-after-cycle` sentinel check in `cycle_post.py` must happen **after** the commit, not before. If the agent exits before committing, the state branch falls behind.

**Required**: Place `.stop-after-cycle` check as the last operation in `cycle_post.py` (after commit, after iteration log, after version bump).

### PR Flow / Auto Merge

If an agent is mid-PR-flow when `.stop-after-cycle` is written, the `cycle_post.py` commit will include whatever the agent output in `cycle-output.json`. The branch may be in a partial state. On respawn, the agent reads `working-state.md` and resumes.

**Risk**: If `working-state.md` update happens in `_do_working_state_update` (step 3 in `cycle_post.py`), and `.stop-after-cycle` exits after step 6 (commit), the state is consistent. The agent resumes correctly.

**Required**: Ensure `_do_working_state_update` runs before the `.stop-after-cycle` exit point.

### Health Monitoring

`health_check.py` currently shows STOPPED for agents with `.stop` sentinel. Under the new model:
- Agents that are cleanly waiting for respawn (wrapper between cycles) show `dead` temporarily (heartbeat stops while claude is not running, wrapper may pause between cycles)
- This creates false STALLED readings during the inter-cycle gap

**Mitigation**: Add a new health state `restarting` (already exists as a legacy status string). Wrapper writes `restarting|{reason}` to `.health` during the inter-cycle wait (between clean exit and respawn). `health_check.py` already maps `restarting` to HEALTHY. No change to `health_check.py` needed — just ensure the wrapper writes `restarting` status to `.health` during the gap.

### `.booting` Sentinel Conflict

`boot_remote.py` uses `.booting` (TTL 30s) to prevent concurrent spawns. If `start_team.py` imports `boot_remote._spawn_terminal`, it will still use this mechanism. No conflict — this sentinel is purely for spawn-time deduplication.

## Open Questions

1. **Wrapper crash recovery without PM auto-boot**: Under the new model, a dead wrapper stays down until a human manually runs `start_team.py --role <name>`. Is this acceptable for production deployments? The old behavior (PM auto-boots each cycle) was more resilient but noisier. Recommendation: keep PM's health-check on cycle 1 of each session (not every cycle) but add a quiet background check every N cycles (e.g. cycle 1, 10, 20...) that only reports, never boots.

2. **Context pressure threshold for wrapper vs. agent**: The wrapper would read `context-pressure` after each claude exit. Should it also write `.stop-after-cycle` if pressure is above threshold *at startup* (pre-spawn check)? Current agent behavior reads it at the start of the cycle. The wrapper-based check would only trigger after cycle completion. Edge case: an agent with 89% context starts a cycle, completes it (context hits 95%), cycle_post exits cleanly — wrapper reads `context-pressure` (which contains the end-of-cycle reading) and respawns. This is fine.

3. **Crash vs. clean exit disambiguation**: Currently, non-zero exit = crash. Zero exit = intentional stop. Under the new model, zero exit + `.stop-after-cycle` = "please respawn me cleanly". Zero exit without `.stop-after-cycle` = "I am done, wrapper can stop". Should the wrapper treat any zero exit as "please respawn" (default looping) or only respawn when `.stop-after-cycle` is present? Recommendation: zero exit without sentinel = wrapper exits (current behavior preserved). Zero exit with `.stop-after-cycle` = wrapper respawns. This avoids infinite loops on intentional clean exits.

4. **`start_team.py` as the only entry point vs. as an optional addition**: Should the old `start-squad.ps1/sh` be removed immediately, or coexist? Recommendation: keep `start-squad.ps1/sh` as thin wrappers calling `start_team.py` during transition. Remove after one version.

5. **Does DM still need `reboot_agent.py`?**: The DM template (`agent-lifecycle.md`) references `reboot_agent.py` for post-ship reboots. Under the new model, DM would call `start_team.py --reboot <role>`. The `agent-lifecycle.md` sub-skill needs updating. `reboot_agent.py` should be kept as a shim initially.

6. **Who writes `.stop-after-cycle` for context pressure?** Two options:
   - Option A: Wrapper polls `context-pressure` file every N seconds in a background job, writes `.stop-after-cycle` when threshold exceeded
   - Option B: `cycle_post.py` reads `context_pressure.exceeded` from `cycle-input.json` (already computed by `cycle_pre.py`) and writes `.stop-after-cycle` instead of `.restart`

   Option B is cleaner — `cycle_post.py` already has the context pressure data (it's in `cycle-input.json`). The agent no longer needs to signal it; `cycle_post.py` makes the decision mechanically. This keeps the wrapper simple (no background polling). **Recommended: Option B.**

## Recommendation

**Proceed with implementation**. The design is sound and addresses a real fragmentation problem. The key changes are straightforward:

**High-confidence, implement immediately:**
- New `start_team.py` (imports `boot_remote` spawn logic, replaces `start-squad.ps1/.sh`)
- `.stop-after-cycle` sentinel check in `cycle_post.py` (replaces `_do_restart_sentinel` for context pressure)
- Wrapper loop (replaces single-shot respawn) with `.stop` as the only brake
- Remove `self-restart.md` sub-skill from all templates

**Needs human decision first:**
- Whether PM should retain any auto-boot capability for dead wrappers (see Open Question 1) — recommend: no, but add periodic health report every 10 cycles
- `.restart` vs `.stop-after-cycle` naming and the transition period

**Implementation risk: LOW** — the sentinel infrastructure already exists. The main work is (a) replacing the wrapper's single-shot restart with a loop, (b) moving the "should I restart?" decision from agent output to `cycle_post.py`, and (c) creating the `start_team.py` entry point. All changes are in well-understood files.

**Testing requirements:**
- Comprehension test: agent templates no longer contain `restart_needed` and do not write `.restart`
- Integration test: wrapper loop respawns after `.stop-after-cycle`, stops after `.stop`
- Integration test: `cycle_post.py` writes `.stop-after-cycle` when context pressure exceeded
- Integration test: `start_team.py --reboot` triggers clean respawn
- Edge case test: wrapper exits cleanly when `.stop` + `.stop-after-cycle` coexist
