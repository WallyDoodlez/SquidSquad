# SquidSquad E2E Test Plan — External Validation

Run by a Claude agent against test projects. Tests functionality that cannot be verified from within SquidSquad itself.

## Prerequisites

- Fresh GitHub repo (test project) with some source code (e.g., a simple Python CLI app)
- SquidSquad skill installed (`/squidsquad-setup` completed)
- `gh` CLI authenticated with repo scope
- Claude Code CLI available

---

## Category 1: Setup Flow

### E2E-1: Fresh install on empty project
- **Setup**: Create new GitHub repo with a README and a simple Python script
- **Steps**: Run `/squidsquad-setup` in the repo
- **Verify**:
  - `.squidsquad/` directory created with config.md, agent dirs
  - config.md has correct project name and repo URL
  - Dev agent CLAUDE.md generated by compose.py
  - Boot scripts exist (start-[role].sh / .ps1)
  - GitHub labels created (type:issue, type:task, status:*, role:*, squidsquad)
  - `.squidsquad/vault/` initialized with BRIEFING.md

### E2E-2: Setup with custom team shape
- **Setup**: Fresh repo
- **Steps**: Run setup, choose non-default team (e.g., 2 dev agents: "fe" and "be", no DM)
- **Verify**:
  - config.md lists both dev agents
  - Separate CLAUDE.md generated for each dev agent
  - Boot scripts for each agent
  - PM template references both agents

### E2E-3: Setup on existing project with code
- **Setup**: Repo with existing src/, tests/, package.json or requirements.txt
- **Steps**: Run `/squidsquad-setup`
- **Verify**:
  - Setup detects project type (language, framework)
  - Test command auto-detected and written to config.md
  - No existing files overwritten or deleted

## Category 2: Agent Boot & Lifecycle

### E2E-4: Single agent boot
- **Setup**: Completed setup from E2E-1
- **Steps**: Run the boot script for PM (`start-pm.sh` or `.ps1`)
- **Verify**:
  - Agent starts and prints cycle 1 header
  - `.health` file written with `alive` status
  - `.pid` file written with correct PID
  - `current-state` file updated each step
  - Agent completes cycle 1 and writes iteration log

### E2E-5: Agent reads and follows CLAUDE.md
- **Setup**: Boot PM agent
- **Steps**: Let it run 1 cycle, observe behavior
- **Verify**:
  - Pulls latest (git pull)
  - Checks context pressure
  - Runs health check
  - Checks for external issues
  - Logs iteration
  - Commits and pushes

### E2E-6: Agent self-restart on template change
- **Setup**: Running agent (any role)
- **Steps**: Modify the agent's CLAUDE.md (add a comment), wait for cycle end
- **Verify**:
  - Agent detects mtime change on CLAUDE.md
  - Writes `.restart` sentinel
  - Boot wrapper restarts the agent
  - New session reads working-state.md and resumes

### E2E-7: Agent stop via sentinel
- **Setup**: Running agent
- **Steps**: Create `.squidsquad/[role]/.stop` file
- **Verify**:
  - Agent completes current cycle
  - Does not start next cycle
  - Health check reports "stopped"
  - Watchdog does not restart it

## Category 3: Full Ticket Lifecycle

### E2E-8: Bug filed → dev fixes → QA verifies → DM ships
- **Setup**: Running squad (PM + 1 dev + QA + DM)
- **Steps**:
  1. Human tells PM about a bug in the test project (e.g., "function X returns wrong value")
  2. PM investigates and files issue
  3. Wait for dev agent to pick up, implement fix, mark pending-test
  4. Wait for QA to verify, merge PR, mark pending-ship
  5. Wait for DM to ship
- **Verify**:
  - Issue transitions: open → in-progress → pending-test → pending-ship → shipped
  - PR created as draft by dev
  - PR merged by QA (not DM, not PM) before marking pending-ship
  - Fix is on main after shipping
  - Issue auto-closed by tracker.py on shipped transition
  - Dev wrote tests for the fix
  - QA promoted test files to tests/ (per #1637)

### E2E-9: Feature task — full 5-phase lifecycle
- **Setup**: Running squad
- **Steps**:
  1. Human requests a feature (e.g., "add a --verbose flag to the CLI")
  2. PM files as Pending, human approves planning
  3. PM runs Phase 1 (Research), Phase 2 (Discussion with human), Phase 3 (Test Plan)
  4. Human approves execution
  5. Dev implements, QA verifies, DM ships
- **Verify**:
  - Status transitions: pending → planning → planned → approved → in-progress → pending-test → pending-ship → shipped
  - RESEARCH.md, CONTEXT.md, TEST-PLAN.md created in planning/
  - Human was asked interactive questions (Phase 2)
  - Test plan has comprehension questions (if template change)
  - QA executed test plan and promoted tests
  - Feature works in the test project

### E2E-10: Merge gate enforcement
- **Setup**: Running squad with branch workflow enabled
- **Steps**:
  1. File a bug, let dev fix it on a branch with PR
  2. Attempt to transition directly to shipped without merging
- **Verify**:
  - tracker.py blocks the transition
  - Error message names the unmerged PR
  - --force does NOT bypass the gate

### E2E-11: Draft PR auto-conversion
- **Setup**: Running squad, PR exists as draft
- **Steps**: QA marks item pending-ship
- **Verify**:
  - tracker.py auto-converts draft PR to ready on pending-test→pending-ship transition
  - DM can proceed with delivery without manual intervention

## Category 4: Multi-Agent Coordination

### E2E-12: Concurrent agent git operations
- **Setup**: 2+ agents running in separate clones, both actively committing
- **Steps**: Let agents run for several cycles
- **Verify**:
  - No git conflicts that crash agents
  - git_ops.py stash/pop handles concurrent changes
  - Agents successfully pull each other's commits

### E2E-13: Health check cross-clone detection
- **Setup**: Multi-clone setup with .local-config pointing to each clone
- **Steps**: Kill one agent, run health check from another
- **Verify**:
  - health_check.py detects dead agent via PID check
  - Reports correct health status (stalled, not healthy)
  - Living agents reported as healthy

### E2E-14: Pipeline sentinel stall detection
- **Setup**: Running PM, create an issue and manually set it to in-progress
- **Steps**: Don't let any agent touch it for 90+ minutes
- **Verify**:
  - PM sentinel detects stall
  - Comments on the issue with nudge
  - If assigned agent is dead, transitions back to approved

## Category 5: Upgrade Flow

### E2E-15: Upgrade existing install
- **Setup**: Install SquidSquad at version N, run a few cycles
- **Steps**: Upgrade to version N+1 via `/squidsquad-upgrade`
- **Verify**:
  - Agent templates recomposed from updated references/
  - Config.md updated with new fields (if any)
  - Existing issues/tasks preserved
  - Agents restart with new instructions
  - No data loss in vault/

### E2E-16: Upgrade with local SOUL.md modifications
- **Setup**: Existing install with customized SOUL.md
- **Steps**: Run upgrade
- **Verify**:
  - SOUL.md not overwritten (user customizations preserved)
  - CLAUDE.md regenerated from updated sub-skills
  - Custom soul content still present after upgrade

---

## Category 6: Edge Cases & Failure Modes

### E2E-17: Agent crash mid-cycle
- **Setup**: Running agent with in-progress task
- **Steps**: Kill the agent process (SIGKILL / taskkill)
- **Verify**:
  - Working state preserved from last checkpoint
  - Watchdog (or boot script) detects dead PID and restarts
  - New session resumes from working-state.md
  - In-progress task not corrupted

### E2E-18: GitHub API unavailable
- **Setup**: Running agent
- **Steps**: Temporarily block GitHub API (e.g., firewall rule, or revoke token)
- **Verify**:
  - Agent prints "GitHub unreachable" and skips tracker operations
  - Does not crash
  - Retries next cycle
  - Local files (iteration logs, working state) still written

### E2E-19: Empty project — no issues, no tasks
- **Setup**: Fresh install, no work filed
- **Steps**: Let agents run 5+ cycles
- **Verify**:
  - Quiet cycles logged correctly
  - No errors from empty tracker queries
  - Improvement scanning triggers after 3 quiet cycles (if enabled)
  - No spurious issues filed

### E2E-20: Version bump trigger
- **Setup**: Set Ship Threshold to 3, ship 3 items
- **Steps**: Let DM/PM delivery handle the bump
- **Verify**:
  - Version incremented in config.md and SKILL.md
  - CHANGELOG.md updated with shipped items
  - Git tag created and pushed
  - Counter reset to 0

---

## Execution Notes

- Each category can run independently
- Categories 1-3 are highest priority (core functionality)
- Test projects should be disposable (create, test, delete)
- Agent should report PASS/FAIL per test case with evidence (commands run, output observed)
- Estimated time: Categories 1-3 require real agent cycles (30m+ each), Categories 4-6 require multi-hour runs
